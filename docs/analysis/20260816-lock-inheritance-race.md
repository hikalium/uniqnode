# 二重オープン検査の単発失敗の根本原因: fork→exec 窓での錠FD継承

<a id="200fc085-1dc4-4eed-9c64-d1f3545d0876"></a>

日付: 2026-08-16。対象: ストアの二重オープン防止錠(Linux 抽象名前空間の UnixListener)。
発端: `double_open_of_the_same_directory_is_rejected` がワークスペース全体の並列実行で
一度だけ「解放後は開ける」に失敗し、単独実行・再実行(計8回)では再現しなかった。

## 問い: 決定論的なテストがなぜ再現しないのか

決定論的なのはテスト内部のロジック(種付き乱数・条件ポーリング)であって、この失敗は
テストの外側 — 同一プロセス内の別スレッドが行う子プロセス生成という、OS レベルの
環境競合 — で起きていた。だから同じテストを何度回しても、隣で走るテストの構成と
タイミングが揃わない限り再現しない。

## 機構

1. `std::process::Command` の子プロセス生成は fork(vfork)→exec で行われる。
2. fork の瞬間、子は親の全ファイル記述子の複製を持つ。CLOEXEC フラグが付いていても、
   それが閉じられるのは exec の瞬間であって fork の瞬間ではない。
3. 抽象名前空間の UNIX ソケットは、その名前を参照する最後の FD が閉じるまで束縛が残る。
4. したがって「錠を drop → 直後に同じ名前を bind」する列が、別スレッドの fork→exec の
   窓と重なると、子の FD 複製がまだ名前を握っていて AddrInUse になる。
5. lib テストは1プロセス内で並列に走り、`ed25519::tests::openssl_interop` が openssl を
   繰り返し spawn する。全体並列実行では統合テストのプロセス群が機械を圧迫して
   fork→exec の窓が延び、一度だけ重なった。

## 再現と計測

8スレッドが `/bin/true` を spawn し続ける傍らで bind→drop→即再 bind を繰り返す
40行の実験プログラム(標準ライブラリのみ)で決定的に再現した:

- 100,000 周期中 1,437 回(1.4%)が AddrInUse。
- 複製 FD の解放(= 再 bind 可能になる)までの待ちは最悪 3,576 マイクロ秒。

## 対処

`acquire_lock` の AddrInUse を有界の再試行(1ms 間隔、上限 250ms = 実測最悪値の約70倍)に
変えた。本物の保持者は解放しないので、上限まで塞がっていれば二重オープンと確定できる。
判別の意味論は変わらず、変わるのは「本物の二重オープンの検出が最大 250ms 遅れる」ことだけ。

確率的な競合を在庫のテストにはしない(should/0125: 決定的でないテストは置かない)。
機構と数値は本文書が記録し、再現プログラムの構成も上に書いた(必要なら数分で再作成できる)。

## 教訓

- 「決定論的なテスト」の決定論はプロセス境界で終わる。同一プロセス内の spawn は、
  CLOEXEC を付けていても fork→exec の窓で全 FD を一瞬共有させる。
- FD ベースの錠(ソケット・flock)はこの継承の影響を受ける。fcntl のレコードロックは
  受けないが、標準ライブラリだけでは扱えないため、有界再試行を選んだ。
