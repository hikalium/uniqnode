# PACK_GC — pack の書き直しによる物理回収と、機会層の evict(設計草案)

<a id="f272eeda-8664-42da-9e5c-ef354bc3f3a7"></a>

[docs/plan/RAG.md](#4ed764d8-a570-4809-bd0c-80de0d4b5545) の項目 8 の設計である。実装済み
なのは、生きているオブジェクトの定義と、それで pack ごとの孤児量を数える
`uniqnode gc <dir> --dry-run` だけで、[docs/design/GC.md](#9b1ceac3-f3cf-4595-87cb-6e40ce0900e5)
に住む。ディスクを書き直す回収と evict は未実装で、この文書が扱う。読み手は、この層を実装
する者と、その設計を審査する者。現在のストアの姿は
[docs/design/OVERVIEW.md](#cfa85cc2-0d72-49f2-b628-b9622589851b) と SPEC §5 にあり、ここでは
設計を定めるのに必要な最小限だけを繰り返す。末尾の「セルフレビュー」が、この草案の未決
事項と、実装前に決めるべき順序である。

## 目的

ストアは追記専用で、封印された pack は二度と変わらない。それがクラッシュ耐性と無停止
バックアップの源である一方、消す手段が一つも無い。ref を tombstone にしても、上書きしても、
指していたオブジェクトのバイト列は pack に残る。`capacity_bytes` を設定すると上限を超えた
put は拒否されるが、空ける手段が無いので、いっぱいになったら書けなくなるだけである。

この層が足すのは 2 つの能力で、依存の向きは一方向である。

1. 物理回収(compaction): どこからも参照されないオブジェクトを含む封印済み pack を、生きて
   いるオブジェクトだけを写した新しい pack で置き換え、ディスクを取り戻す。消す判断を含ま
   ない。既に誰も指していないものを回収するだけなので、安全側に閉じている。
2. evict: 容量が逼迫したとき、機会層(SPEC §5.4)のオブジェクトを選んで「参照されない」
   状態にし、1 に渡す。消す判断を含む。間違えるとデータを失う。

1 は evict が無くても単体で価値がある(再取り込みで置き換えられた旧チャンク、tombstone した
ページの写し、途中で失敗した取り込みの残骸は、今の本番ノードにも既にある)。2 は 1 が
無ければ意味を持たない(選んでも消えない)。だから 1 を先に作り、固めてから 2 に進む。

同じ層の残りとして `renditions/` の輸出除外([docs/design/RENDITION.md](#6046eeca-1d95-4d47-87da-13f86c7710dc)
の「既知の癖」)があり、末尾で扱う。

## 前提となる現在の姿

- オブジェクトは `packs/pack-NNNNNN.pack` に `[len][crc32][payload]` で追記される。既定
  256 MB で封印し、封印済み番号の一覧を MANIFEST に atomic rename で書く。オブジェクト ID →
  (pack, offset) の索引はメモリ上の導出データで、起動時に全 pack を走査して作る。
- 起動時の回復は「番号順に走査し、封印済みでない最後の 1 本だけがアクティブ(torn tail を
  切り詰めてよい)」という順序の仮定に立つ。番号の最大が封印済みなら次の番号を新しい
  アクティブにする。
- ref・pin・保持表明は `reflog/` に署名付きで追記され、署名者ごとの seq が連続している
  ことを同期が要求する(SPEC §7.3 MUST)。
- 確約層と機会層の区別はデータとしては既にある: 自分が保持表明(attest held)を出した root が
  確約層、それ以外が機会層。pin は「root の閉包に min_replicas を要求する」レコードで、pin を
  出した者は同時に attest も出す(api.rs)。取り込み(ingest)は ref を作るだけで pin も attest
  も出さない。
- fsck の不変条件: 自分の名前空間の ref が指す先は必ず存在する(欠けは破損)。他ノードの ref
  の先は無くてよい(開世界。`foreign_targets_absent` として数える)。
- backup は封印済み pack を「写し先に同じ大きさで在れば写さない」増分で写し、MANIFEST を
  最後に据える。写し先だけにあるファイルは消さない([docs/mop/BACKUP.md](#e026a5e7-1ece-4f4e-b6b8-ee96c62883a2))。
- 検索索引(BM25)は `is_current` が object_count の変化を見て作り直す。埋め込みベクトルの
  キャッシュ(`derived/`)はオブジェクト ID を鍵に追記され、消す道は無い。

## 段階 1: 物理回収(compaction)

### 生きているオブジェクトの定義

[docs/design/GC.md](#9b1ceac3-f3cf-4595-87cb-6e40ce0900e5) にある(実装済み。根 = 全署名者の
ref の target・pin の root・held=true の保持表明の root、閉包は `reachable_closure` と同じ
規約)。他ノードの ref が指す先を根に含めるので、それを外せるのは段階 2 の evict だけである。

### 単位と対象

回収の単位は封印済み pack 1 本である。アクティブな pack には触れない(追記中で、書き手と
競合する)。pack ごとの孤児率と、閾値(既定 0.25)を超えた pack を対象と見る判定は
GC.md の `gc --dry-run` が既に出す。閾値の根拠は下の未決事項 1。1 回の実行で複数の pack を
まとめて 1 本(またはサイズ上限で数本)の新しい pack に写してよい。

### 手順

```
A. 錠の中で:  生きている集合 L を計算し、封印済み pack の一覧と last_seq を写し取る
B. 錠の外で:  対象 pack の各レコードを走査し、ID ∈ L のものだけを tmp/ の新しい pack へ
              追記する(封印済みは不変なので錠なしで読める)。fsync。
C. 錠の中で:  A の後に reflog へ追記があったか(last_seq の変化)を見る。あれば中止して
              次回に回す(捨てる集合 L̄ の要素が新しい ref に指された可能性を排除する
              最も単純な方法)。無ければ:
              1. アクティブ pack を封印する(番号 a)。
              2. 新しい pack を番号 a+1 として packs/ へ rename し、封印済みとする。
              3. MANIFEST を書く: sealed_packs から対象を外し、a と a+1 を加える。
              4. 索引を新しい位置に差し替え、used_bytes を減らす。
              5. アクティブを a+2 で開く。
D. 錠の外で:  対象だった旧 pack ファイルを削除する(MANIFEST に無いので、消す前に
              クラッシュしても回復は「封印済みでも最後でもない未知の pack」として扱う。
              下の「回復の変更」)。
```

C-1 と C-2 の順序は、回復の「封印済みでない最後の 1 本がアクティブ」という仮定を守るため
にある。新しい封印済み pack の番号がアクティブより大きくなると、アクティブが「最後」で
なくなり、torn tail を持っていれば破損と誤判定される。アクティブを先に封印すれば、
a < a+1 < a+2 の順が保たれる。

C の「中止して次回」は最初の版のための単純化で、A と C の間に書き込みが 1 つでもあれば
やり直しになる。書き込みが絶えないノードでは永久に進まないので、次の版では L̄ の各要素に
ついて「A 以後に追加された根から到達可能か」だけを再計算する(差分検査)。書き直しの成果物
(B)は再利用できる。

### 回復の変更

MANIFEST に無く、最後でもない pack ファイルが現れうる(D の前のクラッシュ)。今の回復は
そのファイルを未封印として走査し、torn tail があれば破損と言う。変更後は、MANIFEST に無く
最後でもない pack は「回収済みの残骸」として走査せず、ログに名を出して削除する。この規則が
成り立つのは、封印済みの一覧が MANIFEST に完全に書かれているときだけなので、MANIFEST が
無い(初回封印前の)ストアは今の規則のままにする。

fsck に「MANIFEST に無く最後でもない pack がある」を報告として足す(エラーではなく事実)。

### クラッシュの各点

| 落ちる点 | 状態 | 回復 |
|---|---|---|
| B の途中 | tmp/ に書きかけの新 pack | tmp/ は起動時に空にする(今もそう)。旧 pack は無傷 |
| C-1 の後 | アクティブが封印済み。新 pack は tmp/ | 次の起動で a+1 がアクティブになる。回収は次回やり直し |
| C-2 の後、C-3 の前 | packs/ に a+1 があるが MANIFEST に無い。最後なので未封印と扱われる | 走査され、中身は旧 pack と重複(索引は最初の 1 つだけ数える)。無害。次回の回収で対象になる |
| C-3 の後、D の前 | MANIFEST は新。旧 pack が残る | 「回収済みの残骸」として削除される |

MANIFEST が参照するファイルは参照される前に fsync 済み(SPEC §5.2 MUST)を、新 pack の
rename と MANIFEST の rename の順で守る。

### 起動の口

`uniqnode gc <dir> --dry-run [--threshold <割合>]` は実装済み
([docs/design/GC.md](#9b1ceac3-f3cf-4595-87cb-6e40ce0900e5))。`--dry-run` 無しは回収未実装を
言って 2 で終わるので、回収が入るときはそこを実装に差し替える。serve への組み込み(周期
または容量契機)は、手で何度か回して観測してから決める(should/0116)。serve が錠を持って
いる間は gc は別プロセスとして走れない(A と C が錠を要る。dry-run も開くので同じ)ので、
組み込みまでは serve を止めて打つか、`POST /v1/admin/gc` を足す。

### 周辺への影響

- backup: 写し元の MANIFEST から消えた pack が写し先に残る。今の規則(写し先だけの
  ファイルは消さない)では、写し先を開くときそれらが「未封印」として走査され、torn tail
  があれば破損と誤判定される(そして回収前の孤児が写し先で生き返る)。backup は
  「写し元の MANIFEST に無い pack は写し先から消す」に変える。MANIFEST が権威なので安全で、
  設定ファイルを消さない規則はそのままにする。BACKUP.md の「意図的に持たないもの」を直す。
- 検索索引: object_count が減るので `is_current` が作り直しを起こす。追加の手当は不要。
- 埋め込みキャッシュ: 消えたオブジェクトのベクトルが `derived/` に残る。害は容量だけ
  なので、`uniqnode embed` にキャッシュの詰め直しを足すのは別の小さな項目にする。
- 分散検索・同期: 孤児は定義により誰の ref からも指されていないので、ピアから GET されうる
  のは「相手が古い ref を持っている」場合だけで、404 は開世界の正常な答えである。

## 段階 2: evict(機会層の追い出し)

### 何を守り、何を出せるか

守る(絶対に消さない):

- 自分の名前空間の ref が指す先とその閉包。fsck の不変条件がこれを要求している。
  取り込んだ文書はここに入るので、単一ノードで RAG として使う限り自分の知識は消えない。
- 自分が保持表明した root の閉包(確約層。SPEC §5.4 MUST NOT)。
- 上の 2 つから参照されているもの(参照カウント。SPEC §5.4 SHOULD)。

出せる(機会層): それ以外、すなわち他ノードの ref・pin・保持表明だけが根になっている
オブジェクト。同期で流れてきた複製がこれである。

SPEC §5.4 は「min_replicas=0 のオブジェクトは作成者自身の複製も evict してよい」と言う。
上の「自分の ref の先は守る」は、これを実装上の不変条件で狭めている(作成者の ref が
生きている限り、その複製は消えない)。作成者が本当に忘れたいなら tombstone すればよく、
そのとき段階 1 が回収する。この読み替えは SPEC の MAY を使わないだけで、MUST には触れない
(未決事項 4)。

### 単位

閉包の根ごとに出す。文書 = root + チャンク群 なので、チャンクだけを抜くと文書が壊れる。
出す候補は「機会層の根」で、根を出すと決めたら、その閉包のうち守るべき集合に含まれない
ものを L̄ に加える。

### 順序

SPEC は LRU を基本と言うが、ストアは「最後に読まれた時刻」を持たない(読みは状態を変えない
のが設計の基本)。最初の版は「最後に取り込まれた順」(その根を指す ref レコードの `at` の
新しい順。古いものから出す)で代える。決定的で、既に reflog にある情報だけで決まる。本当の
LRU が要るかは、機会層の複製がどう使われるかを観測してから決める(未決事項 5)。

### 契機と量

`capacity_bytes` が設定されているときだけ動く。低水位(既定: 容量の 90%)を超えたら、
高水位(既定: 80%)を下回るまで出す。put_object が容量超過で拒否する前に evict を試み、
それでも足りなければ今と同じく拒否する。同期の取り寄せ(fetch_closures)も put_object を
通るので同じ道を通る。健全性エンジンの修復が複製を取り寄せて attest すれば確約層に
なり、降格(attest 撤回)で機会層に戻る。evict と健全性の状態機械はこの 2 つの記録だけで
繋がっていて、新しい状態は足さない(should/0130)。

evict は L̄ を決めるだけで、ディスクは段階 1 が回収する。したがって容量逼迫時の evict は
即座に compaction を伴う必要があり、その間 put は待たされる。回収の対象は「出した根が
入っている pack」で、閾値は無視して回す。

### sim との対応

sim/ の evict は「LRU 末尾から、ローカル確約層が参照していないものを優先して追い出す」で、
上の設計はこれを「取り込み順で代え、自分の ref の先も守る」に置き換えたものである。
sim の性質(確約層は消えない、参照されるものは温存)はそのまま成り立つ。順序の違いで
複製数の性質は変わらない(どれを出しても機会層で、健全性は保持表明だけを数える)。

## `renditions/` の輸出除外

ページの写しは `renditions/<原本 ID>/<頁>/<レシピ>` という自分の ref である。伝播交換は
署名者ごとの ref レコードを seq 連続で運ぶので、名前で選んで送らないことは、そのままでは
できない: 抜けた seq を受け手が「飛び」として拒否する(SPEC §7.3 MUST)。

取れる道は 3 つある。

- (a) 送り手が抜いた seq に、同じ seq で中身を伏せた別のレコードを署名して送る。同じ
  署名者・同じ seq に内容の違うレコードが世界に 2 つ存在することになり、「seq が
  レコードを識別する」性質を弱める。
- (b) 写しを ref ではなく `derived/` に置く(導出データとして扱う)。伝播しなくなり、除外の
  問題は消える。しかし RENDITION.md の「導出データをストアに入れる条件」(レシピが揃って
  いれば言明として扱う)という判断を覆すことになり、写しが content-addressed で検証
  できる性質と、他ノードに配れる性質を捨てる。
- (c) 写しの名前空間を別の署名者にする(ノード鍵から導出した副鍵で署名する)。伝播交換は
  署名者単位なので、副鍵の記録を送らなければ除外が成る。seq の連続も保たれる。ノードが
  複数の署名者を持つことになり、fsck の「自分の ref」の判定と、同期の署名者一覧に
  変更が及ぶ。

推奨は (c) である。除外したいのが写しだけである限り、これが SPEC の MUST に触れず、写しの
性質も捨てない唯一の道である。ただし規模は 3 つの中で最大で、項目 8 の本体(段階 1・2)
とは独立に進められるので、別の項目に切り出すことを提案する(未決事項 7)。

なお、段階 2 の evict は写しの回収には効かない(自分の ref の先は守るため)。写しを消す
のは応用層の判断(一定期間見られていない写しの ref を tombstone する)で、それが段階 1 の
入力になる。写しの「最後に見られた時刻」はビューワが持てる(導出データ)。

## テスト計画

- 統合(node/tests/gc.rs に足す。dry-run の分は既にある): 小さい封印閾値で複数 pack を
  作り、上書きと tombstone で孤児を作って gc → 生きているものが全件読め、fsck 緑、
  used_bytes とディスクが減っている。A と C の間に書き込みを挟むと中止して何も変わらない。
  gc の後の backup が写し先の旧 pack を消し、写し先の fsck が緑。
- クラッシュ(crash.rs に列を足す): C-1、C-2、C-3、D の各点で SIGKILL し、毎回の回復と
  fsck 全件パス。tmp/ の掃除。
- モデル(sync_model.rs に足す): 書き込み・tombstone・同期・gc・evict・再起動を無作為に
  交錯させ、「自分の ref の先と確約層は一度も欠けない」「全対同期後に収束する」を固定する。
- 評価: 本番で 1 回回して所要と戻った容量を測る(dry-run の初回実測は
  [docs/analysis/20260905-gc-dry-run.md](#491c8c79-620b-47d4-b914-65279e6a599e))。

## 完了条件

- `capacity_bytes` を小さくしたノードに上限以上を書いても、機会層が出されて書き続けられ、
  自分の ref の先と確約層は一切消えない(モデルテストで固定)。
- 回収の最中に SIGKILL しても fsck が緑。
- 回収後の backup が増分のまま正しく、写し先の fsck が緑。
- 本番ノードで 1 回回し、所要と戻った容量が BACKUP.md の実測と同じ形で記録されている。

## セルフレビュー: 未決事項と、実装前に決める順序

1. 閾値 0.25 の根拠が無い。`gc --dry-run` の初回実測
   ([docs/analysis/20260905-gc-dry-run.md](#491c8c79-620b-47d4-b914-65279e6a599e))では、
   本番の写し 377 MB の孤児は 1 件・398 バイトで、ref 204 本に tombstone は無く、どの閾値
   でも対象は 0 本だった。閾値を決める材料は、孤児を作る運用(内容を変えた再取り込み、
   写しの tombstone)が起きてから dry-run を打ち直して得る。それまで回収を急ぐ容量上の
   理由も無い。
2. C の「書き込みがあれば中止」は、書き込みが絶えないノードで進まない。差分検査(A 以後の
   新しい根からの到達可能性だけを見る)が次の版の必須事項で、その正しさは「L̄ の要素が
   生き返る唯一の道は新しい根からの到達」という主張に依る。set_ref が target の存在を要求
   するので、孤児を指す新しい ref は作れる(生き返りは実際に起こる)。主張自体は正しいが、
   pin・attest の root も同じ扱いにすることを忘れない。
3. 回復の「MANIFEST に無く最後でもない pack は残骸」という規則は、MANIFEST を失った
   ストアで危険である(全部が残骸に見える)。MANIFEST の欠落は今も「全部未封印」として
   扱われ、それは torn tail の切り詰めを許す側に倒れている。残骸の削除は「MANIFEST が在る
   ときだけ」に限り、MANIFEST が無ければ削除せず報告だけにする。この場合分けをテストで
   固定する。
4. SPEC §5.4 の「作成者自身の複製も evict してよい」を使わない読み替えは、単一ノードの RAG
   としての使い勝手を守るためだが、SPEC の意図(min_replicas=0 は世界が忘れてよい)からは
   後退である。SPEC に L1 の具体化として「作成者の ref が生きている複製は evict しない
   (fsck の不変条件による)」を 1 文足すか、逆に fsck の不変条件を緩めるかを決める。前者を
   推奨する(不変条件は破損検知の要で、緩めると失うものが大きい)。
5. LRU を「取り込み順」で代えるのは観測不足の暫定である。機会層の複製が検索で読まれる頻度
   を測る手段(検索の出典に含まれた回数の集計。導出データ)を先に足せば、本当の LRU にも
   その統計が使える。段階 2 の前に決める。
6. 容量逼迫時の evict + 即時 compaction は、put の待ち時間を数秒(実コーパスで pack 1 本の
   書き直しは 100 MB 級)に伸ばす。同期の取り寄せが put を大量に呼ぶ経路で、健全性エンジンの
   「ネットワーク待ちの間ストアの錠を持たない」規律(SPEC §8.2)と干渉しないか。B は錠の外
   なので原理上は干渉しないが、A・C の錠の長さ(生きている集合の計算 = 全閉包走査)は
   実測で 15.2 秒だった(release ビルド、55,433 オブジェクト・377 MB。
   [docs/analysis/20260905-gc-dry-run.md](#491c8c79-620b-47d4-b914-65279e6a599e))。内訳は
   ディスクの読み取り 0.35 秒に対し c1 の構文解析が 14.6 秒(26 MB/s)で、探索ではなく
   参照を拾うための全文の値の組み立てが支配している。A をこの形のまま錠の中に置いては
   ならない。手は 2 つで、どちらも増分維持(ref の適用時に到達カウントを更新する)より
   小さい: (a) 参照の収集を c1 の値を組み立てないバイト列の走査にする(`collect_references`
   と 2 つ目の実装になるので、同じ入力での一致をテストで固定する。逆引き索引の構築にも
   効く)。(b) 封印済み pack は不変なので、その参照の収集を錠の外で済ませ、錠の中では
   根の表の写しと追記中の pack の分だけを見る。段階 1 の実装の前にどちらかを選ぶ。
7. `renditions/` の輸出除外は (c) 副鍵が筋だが、fsck・同期・署名者一覧に手が入り、項目 8 の
   本体と独立である。RAG.md では項目 8 から切り離して新しい番号を振り、順序は段階 1 の後・
   段階 2 の前(写しの tombstone が段階 1 の主要な入力になるので、写しの扱いを先に固める
   価値がある)に置くことを提案する。
8. reflog の肥大は扱っていない。ref の履歴は全部残り、export_ref_records は毎回全 reflog を
   走査する。SPEC §4.4 は「古いレコードは忘却できる」と言うが、同期の since カーソルが
   seq 連続を要求するため、忘却は「ある seq より前を持たないことを宣言する」形でしか
   できず、新しいピアの初回同期が成り立たなくなる。pack GC とは別の問題として起票する。
9. 埋め込みキャッシュの詰め直しと、写しの「最後に見られた時刻」は、どちらも導出データで
   小さい。段階 1 が着地した時点で RAG.md に小項目として足す。
10. 段階 1 の中止判定に last_seq を使うが、last_seq は「自分の署名者の seq」ではなく全署名者
    の最大の適用 seq である必要がある(他ノードの ref の取り込みも根を増やす)。
    `signer_last_seq` の全エントリを写し取って比べる。実装の細部だが、間違えると生き返りを
    見逃すので、ここに書いておく。
