# ASSERTIONS — 言明・検証・訂正の論理設計

<a id="c05379e2-2d30-41bc-8342-62103d94bb21"></a>

読み手は、取り込みと訂正の実装計画([docs/plan/INGEST.md](#11ff6fec-cf85-4ae9-a24c-6098964f6cce))を
実装またはレビューする者と、将来この層の上にモデルを足す者。この文書の仕事は、実装計画の
個々の決定(kind の形、meta に何を入れるか、参照の向き、ref の使い方)が従う論理設計を、
実装の詳細(CLI・API・ファイル配置・外部ツール)から独立に固定することである。実装計画が
「何をどの順で作るか」を持ち、本文書は「なぜその形でなければならないか」を持つ。個々の
実装決定は実装計画側にだけ書き、本文書はそれを導く原理だけを書く(同じ判断を二箇所に
置かない)。

位置づけ: 取り込み層は未実装なので、must/0013 の分類では本文書も plan/ に置く。実装が
着地したら、実装計画の後始末と同時に docs/design/ へ移す(コードに直接は現れないが
実装の基礎方向を成す概念、という design/ の区分に入る)。

## 原理 1(追加のみ): 変化は言明の追加だけで表す

- 言明とは、内容から ID が決まる不変オブジェクトである(I1)。この層で扱う言明は、
  チャンク(この文書のこの文脈にこの本文がある)、注釈(この blob のページ p は節 T を
  含む)、検証記録、訂正の辺、追随の辺。
- 言明は書き換えも削除もできない。世界の変化は二種類しかない: 新しい言明の追加と、
  見え(ref)の張り替え。
- 帰結: 「誤りを直す」という操作は存在しない。あるのは、誤りだと主張する新しい言明を
  足し、見えを新しい側へ張り替えることだけである。

## 原理 2(主張と運用の分離): ID に入るものが主張、入らないものが運用

- 言明の ID は内容の全体から決まる。だから「内容に何を含めるか」の決定は「その言明が
  何を主張するか」の決定そのものである。
- 主張の一部であるもの: チャンクの本文・見出しの文脈・ページ番号。どれが変わっても
  別の主張である。
- 主張の一部でないもの: いつ取り込んだか(時刻)、誰がいまそれを現行と見なすか(見え)、
  どれだけ複製されているか(健全性)。これらは署名付きレコード(ref・pin)の側が持つ(I4)。
- 帰結 1: 同じ入力からは同じ言明しか生まれない(べき等)。時刻を内容に入れた瞬間に
  これが壊れる。
- 帰結 2: 検証は主張の一部ではない。検証を言明の内容に混ぜると、検証のやり直し
  (根拠行の変化)が言明の同一性を変えてしまう。真理の主張と、その主張への信頼の根拠は、
  別のオブジェクトに分ける(原理 4)。

## 原理 3(参照は所有の宣言): 参照の向きは「いっしょに運ぶ」の宣言である

- 参照(s256:)は前方にだけ辿られ、到達閉包が複製・保持の単位になる(SPEC §7.2)。
  したがって「A が B を参照する」と書くことは「A を運ぶ者は B も運ぶ」と宣言することである。
- content-addressing では循環参照が作れない(自分の ID を内容に含めると ID が変わる)ので、
  参照グラフは常に有向非循環であり、この宣言は常に有限に閉じる。
- 帰結 1: 訂正の辺は新旧の言明と検証記録を参照する。訂正を受け取った者は、根拠と
  旧言明ごと受け取る。
- 帰結 2: 逆向きの知識(この言明を参照するものは何か)は言明にできない。それは「いま
  自分が知っている言明の集合」に相対的な事実であり、集合が増えるたびに変わる。だから
  逆引きは導出データとして各 DBノードが手元で再構成する(I4)。
- 帰結 3: 保持させたいのに、どの保持の根からも前方に辿れないものは、束ねの言明(索引)を
  作って ref から指す。保持の根は常に ref である(検証記録がこの例になる)。

## 原理 4(真理の層の分離): 事実・検証・訂正・追随は別の種類の言明である

この四つを混ぜないことが、この設計の中心である。

- 一次言明は世界について述べる(blob B のページ p に節 T がある)。
- 検証記録は照合の実施について述べる(方法 M と根拠 E でこの照合を行った)。真理を作らず、
  信頼の根拠を足すだけである。照合が通ることは真であることの必要条件でしかない。
- 訂正(corrects 型)は言明の真偽について述べる(X は誤りで、Y が代わる)。訂正それ自体も
  言明なので誤りうるし、相反する訂正が共存できる。どれを信じるかは見えと読み手の側の
  判断であり、データ層は裁定しない(開世界)。
- 追随(supersedes 型)は対象の変化について述べる(Y は X の新版対応物)。X の真偽には
  触れない。旧言明は旧 blob についての真のままである。
- 帰結: 照合を通った言明への訂正は、異常系ではなく正常系である。検証は訂正を不要に
  しない。

## 原理 5(見えと歴史の分離): 見えは張り替え、歴史は消えない

- ref は単一書き手の署名付きポインタであり、いまの見えを表す。既定の読み手(検索・RAG)は
  見えだけを読む。
- 旧版・旧言明・訂正は、版の連鎖と訂正の辺から辿れる形で残る。監査する読み手は歴史を
  辿れる。
- 帰結: 「取り消し」は見えからの除去(tombstone)であって、言明の消滅ではない。言明を
  世界から消す操作はこの層に存在しない(物理的な回収は保持と容量の問題であり、真理の
  問題ではない)。

## 原理 6(内容への繋留): 名前は可変、内容は不変 — 主張は内容に張る

- 名前(ref のパス、仕様書の識別子)は可変な指示子であり、同じ名前が時刻によって別の
  内容を指す。
- 世界について述べる言明は、名前ではなく内容(blob のハッシュ)に張る。注釈のページずれ
  (os_dev_specs の data.md で実際に起きた事故)は、可変な名前に主張を張ったことの帰結
  だった。内容に張れば、版の更新は「同じ文書の変化」ではなく「新しい内容の出現」になり、
  旧い主張は偽にならない。
- 名前の役割は一つだけになる: いまこの名前はこの内容を指す、という見えの入口(原理 5)。

## 捨てた代替(論理レベル)

- 言明の上書き(可変な注釈): 帰属と歴史が消え、署名の対象が動く。原理 1 と両立しない。
- 検証を言明の内容に埋める: 検証のやり直しが言明の同一性を変える。原理 2 と原理 4 の
  混同。
- 訂正を削除で表す(旧言明の tombstone だけで済ます): tombstone は見えの操作であって
  主張ではないから、なぜ消えたか・何が代わりかが言明として残らず、旧言明しか持たない
  他の DBノードには何も伝わらない。原理 4 と原理 5 に反する。
- 双方向参照: content-addressing では作れず、必要でもない(逆向きは導出データ。原理 3)。

## 実装計画との対応(この文書の検収の仕方)

この文書の完了条件は、実装計画([docs/plan/INGEST.md](#11ff6fec-cf85-4ae9-a24c-6098964f6cce))の
すべての設計判断が上の原理から導出できることである。導出できない判断が見つかったら、
原理か判断のどちらかが間違っているので、どちらかを直す。主要な対応:

- doc_rev に時刻を入れない・再取り込みの同一性判定 ← 原理 2
- 検証記録の自己完結と、注釈索引の ref ← 原理 3(帰結 2 と帰結 3)
- corrects と supersedes の型の分離・訂正対象の出どころ ← 原理 4
- 注釈を文書名ではなく blob ハッシュに張る ← 原理 6
- 逆引き索引の遅延構築(導出データ) ← 原理 3(帰結 2)

実装の着地時には、冒頭の位置づけのとおり本文書を docs/design/ へ移し、実装計画側の
後始末(参照の張り替え)と同時に行う。
