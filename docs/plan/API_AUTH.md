# API_AUTH: ノードローカル API の信頼の境界を、SPEC §10 と実物で揃える(設計草案)

<a id="abde9b3c-75f8-453b-988e-bfb1e178c771"></a>

版: 第 1 版(2026-10-01)。Claude 側のレビュー待ち。その後に Codex の再レビュー待ち(crystal が止まっている間)。
出所は lamalium の健全性点検(2026-09-30)の項目 12。SPEC.md §10 は「認証は当面固定トークン」と
言うが、コードにトークンは無い。表にも実装済みの口が載っていない。FEED の F2 は、主の口にだけ
`edit`・`retire`・`allow-shrink` を置く設計なので、その前に「主の口を誰が叩けるか」を決める
([docs/plan/FEED.md](#fa8de6f9-59f8-4512-a815-9f41d305db15))。

## 今の事実(2026-10-01 のコード)

| 待ち受け | 本番の束縛 | 認証 | 通すもの |
|---|---|---|---|
| 主の口(serve の `<listen>`) | 127.0.0.1:7440(unit の既定。install の既定も同じで、本番の命令は `--listen` を渡さない) | 無い。送信元も見ない | 全部(`/v1/admin/shutdown`・`/v1/admin/gc`・`PUT /v1/refs/…`・`POST /v1/sync` を含む) |
| 読み口(`--listen-agent`) | 10.10.128.1:7441(wg1) | 無い。送信元は記録に写すだけ | agent_door.rs の許可表(読む口と、許した名への書く口)。外は 403。守りは許可表・wg1 への束縛・install の firewall の 3 重 |
| viewer(`--viewer-listen`) | 0.0.0.0:7450(本番の命令が渡す) | 無い | 読むだけの転送(検索・status・refs・オブジェクトと出典と rendition)。書く口と管理の口は 404 |
| MCP | stdio | 起動した利用者 | 主の口への HTTP |

`POST /v1/peer/query` だけは、中身の QUERY の署名を検証する(§7.1)。これは認証ではなく、
散布された問いの出所の検証である。

コードには在るが §10 の表に無い口: `POST /v1/admin/gc`、`GET /v1/objects/{id}/citation`、
`GET /v1/objects/{id}/rendition`、`GET /v1/objects/{id}/rendition/{alias}`、`GET /v1/closure/{id}`、
`POST /v1/collections/{c}/fetch`、viewer の `GET /`。表に在ってコードに無い口は無い。

## 決めること(案)

案 A を採る: トークンは入れず、信頼の境界を「どこに束縛するか」と「口ごとの許可表」で置き、
SPEC をその形に書き直す。

1. 主の口は、同じ機械の利用者を信頼する口である。認証は無く、全部を通す。ループバックに
   だけ束縛する。管理の口(`/v1/admin/*`)と、FEED の `edit`・`retire`・`allow-shrink` はここに
   だけ置く。
2. 網越しに届く口は、用途ごとに別の待ち受けにし、各々が自分の許可表を持つ: 読み口
   (`--listen-agent`)、FEED の書き口(`--listen-feed`)。許可表の外は 403。束縛は wg1 のような
   限られた網のアドレスにし、install の firewall で送信元を絞る。
3. viewer は読むだけの転送であり、束縛したアドレスに届く全員が全コレクションを読める。
   ループバック以外に置くなら、その網を信頼していることになる。
4. install は、`--listen` にループバック以外のアドレスが来たら断る(新しい検査。今は何でも
   受ける)。2 台目の uniqnode を置くときの `POST /v1/peer/query` と複製の口は、主の口を開く
   のではなく、2 と同じ形の別の待ち受けにする(RAG 項目 10 で設計する)。`uniqnode serve` を
   手で起こす場合(テストや試験の 2 ノード)は検査しない。

採らない案 B(主の口に固定トークン): 主の口に届くのは同じ機械のプロセスで、トークンの
ファイルも同じ機械に置くことになり、守れる相手が増えない。一方で MCP・CLI・viewer・
install の確認・テストの全部にトークンを通す配管が要る。網越しの口に要るのは「誰か」より
「何ができるか」の制限で、それは許可表が持っている。送信元の機械を暗号で確かめる必要が
出たら(wg1 の外から叩かれる形)、そのときに口ごとの鍵(署名済み要求。§6 の鍵を使う)として
設計する。

## SPEC の書き直し(案)

§10 の冒頭の 1 文を、次のように差し替える:

> 管理と利用のための HTTP API。認証は持たず、信頼の境界は待ち受けごとに置く。主の口は同じ
> 機械の利用者を信頼し、ループバックにだけ束縛する(全ての口を通す)。網越しに届く口は用途ごとの
> 別の待ち受けで、各々の許可表の外を 403 で断る(読み口・書き口。INGEST と FEED)。viewer は
> 読むだけの転送で、束縛したアドレスに届く者を信頼する。詳細スキーマは実装マイルストーンで
> 確定する。

表に次の行を足す(本文は既存の行と同じ調子で):
`POST /v1/admin/gc`、`GET /v1/objects/{id}/citation`、`GET /v1/objects/{id}/rendition` と
`/rendition/{alias}`、`GET /v1/closure/{id}`、`POST /v1/collections/{c}/fetch`。

表の下に、待ち受けごとの許可の短い表(上の「今の事実」の表から認証の列を除いたもの)を置き、
読み口の許可表の正典は agent_door.rs の `admit` と docs/design/ の読み口の節である、と書く。

## 操作者に聞くこと

vega の viewer は 0.0.0.0:7450 に束縛していて、install は viewer に firewall を張らない。LAN の
どの機械からも、全コレクションの検索と本文の読み出しができる。lamalium のノートもここに
入っている。これは意図どおりか。意図と違うなら、`--viewer-listen` を 127.0.0.1 か wg1 の
アドレスにするか、viewer にも `--firewall-allow` と同じ形の許可を足す(別の作業項目)。

## 完了条件

- SPEC §10 の冒頭の文・表・待ち受けごとの表が上の形になっている。
- install が `--listen 0.0.0.0:7440` や `--listen 10.10.128.1:7440` を、理由を言って断るテストがある
  (`127.0.0.1`・`[::1]`・`localhost` は通す)。
- FEED.md の「口」の節が、この境界を引いている。
