# 本番ストアの写しに対する `gc --dry-run` の初回実測(55,433 オブジェクト・377 MB)

<a id="491c8c79-620b-47d4-b914-65279e6a599e"></a>

日付: 2026-09-05。対象: 本番ノード(/work2/llm_playground_host_dir/uniqnode-store)の今日の
backup の写し `~/uniqnode-backup`(55,433 オブジェクト、pack 2 本で 377,276,484 バイト、
ref 204 本。中身は本番と同じ)。本番は serve がロックを持っていて gc は開けないので、写しに
対して `target/release/uniqnode gc ~/uniqnode-backup --dry-run` を走らせた。写しは読むだけ
で、実行の前後で MANIFEST・packs/・reflog/ の大きさと mtime が動いていないこと、tmp/ が空
のままであること、続けて走らせた `uniqnode fsck ~/uniqnode-backup` が
`objects: 55433 refs: 204 errors: 0` であることを確かめた。命令の読み方は
[docs/design/GC.md](#9b1ceac3-f3cf-4595-87cb-6e40ce0900e5)、この実測が答えるべき問いは
[docs/plan/PACK_GC.md](#f272eeda-8664-42da-9e5c-ef354bc3f3a7) のセルフレビュー 1(閾値の
根拠)と 6(ロックを持つ長さ)。

## 出力(そのまま)

```
pack 000001 sealed: objects 51668 bytes 269811924, live 269811526, garbage 398 (0.0%) -> keep
pack 000002 active: objects 3765 bytes 107021096, live 107021096, garbage 0 (0.0%) -> keep
gc: packs 2 (sealed 1, compact 0), objects 55433 live 55432 garbage 1, garbage bytes 398 (compact would reclaim 0), roots 202
gc: live set computed in 15157 ms (threshold 0.25, dry-run: nothing written)
```

プロセス全体は 22.05 秒(/usr/bin/time。最大常駐 533 MB)。3 回走らせて、生きている集合の
計算は 15,157 / 15,267 / 15,246 ms、全体は 22.05 / 22.22 / 22.17 秒で、ぶれは 1% 以内。

## 孤児の量(課題 1: 閾値)

孤児は 1 オブジェクト・398 バイトだった。377 MB の 0.0001% である。PACK_GC.md は「再取り込みで
置き換えられた旧チャンク、tombstone したページの写し、途中で失敗した取り込みの残骸は今の
本番ノードにも既にある」と見込んでいたが、写しの ref 204 本に tombstone は 1 本も無く、
再取り込みは同じ内容なら同じ ID に落ちる(put_object はべき等)ので孤児を作らない。残骸と
見られる 1 件だけが残っていた。

ここから言えること。

- 閾値 0.25 の当否を決める材料は、この写しには無い。どの閾値でも対象は 0 本である。
  孤児率の分布を測るには、孤児を作る運用(内容を変えた再取り込み、写しの tombstone)が
  先に起きる必要がある。dry-run はその後に繰り返し打つもので、閾値はそのとき決める。
- 今のストアに対して回収を回しても、戻る容量は 398 バイトである。段階 1 の実装を急ぐ
  容量上の理由は、この時点では無い。段階 1 が価値を持つのは、写しの tombstone(RENDITION の
  「一定期間見られていない写し」)か、文書の差し替えが始まってからになる。
- 追記中の pack 2(107 MB)は閾値と無関係に対象外で、その中の孤児はアクティブが封印される
  まで数字にしか出ない。

## 生きている集合の計算にかかる時間(課題 6: ロックの長さ)

15.2 秒である。回収の手順 A(ロックの中で L を計算する)をこのまま実装すると、書き手は 15 秒
待つ。PACK_GC.md が「秒を超えるなら生きている集合の増分維持が要り、設計の大きさが変わる」
と置いた境目を、1 桁超えている。

内訳を、同じ写しに対して使い捨ての計測(ストアを開き、全オブジェクトを読み、c1 として
解釈して参照を集める、の各段を別々に時計で測る。release ビルド)で取った。

| 段 | 時間 | 備考 |
|---|---|---|
| ストアを開く(全 pack の走査と SHA-256 で索引を作る) | 6,840 ms | gc の集計時間には入らない。fsck 全体が 8.9 秒なので、読み直しと再ハッシュは 2 秒程度 |
| 全 55,433 オブジェクトを get_object で読む | 346 ms | 376,833,020 バイト。ページキャッシュに載っている |
| 全オブジェクトを c1 として解釈し参照を集める | 14,580 ms | 55,233 件が c1、200 件は c1 でない(生の blob)。参照は 56,861 本 |
| gc::plan(根の収集 + 閉包 + pack ごとの集計) | 15,064 ms | うち生きている集合が 15,049 ms |

閉包の 15 秒は、ディスクでも探索でもなく、c1 の構文解析である。377 MB を 14.6 秒で読んで
いるので 26 MB/s。オブジェクトの大半がチャンク本文(数 KB の文字列)で、参照を探すために
その全文を値として組み立てている。

ここから言えること。

- 段階 1 を「A でロックの中で L を計算する」形のまま実装してはならない。手は 2 つある。
  1. 参照の収集を速くする。参照は `s256:` + 16 進 64 桁の文字列で、c1 の値を組み立てずに
     バイト列の走査で拾えれば、14.6 秒は読み取りの 0.35 秒の側に近づく。ただし
     `c1::collect_references` と別の実装になるので、両方を同じ入力に掛けて一致を固定する
     テストが要る(should/0135 の「意図して 2 つ持つとき」の形)。逆引き索引
     (`ReferrerIndex::build`)も同じ全件解析を毎回しているので、同じ速い道が使える。
  2. ロックの外で L を計算する。封印済み pack は不変なので、封印済み pack のオブジェクトの
     参照はロックなしで集められる。ロックの中で要るのは、根の集合(ref・pin・attest の表。
     メモリ上)と、追記中の pack の分だけになる。A のロックは「根の写しを取る」時間まで縮む。
  どちらでも、増分維持(ref の適用時に到達カウントを更新する)を今すぐ設計する必要は
  無い。2 は今のデータ構造だけで成り、1 は PACK_GC.md の差分検査(A 以後に増えた根からの
  到達性だけを見る)にも効く。
- ストアを開くのに 6.8 秒かかる(全 pack の SHA-256)。手で打つ gc では気にならないが、
  serve に組み込むなら開いているストアで計算するので、この分は消える。
- 最大常駐 533 MB は、377 MB のストアに対して全オブジェクトの本体を一度に持たない
  (閉包は 1 件ずつ読む)にしては大きい。索引(55,433 件の ID 文字列と位置)と、閉包の
  seen 集合、ストアを開くときの pack 全体の読み込み(scan_records はファイルをまるごと
  読む: 270 MB の pack 1 本がそのまま常駐の山になる)の合計と見られる。gc の問題では
  なく開く側の癖で、この写しでは害は無い。
