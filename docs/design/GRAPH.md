# GRAPH — 作業グラフの層(恒等ノード・状態ノード・ref・型付きの辺・口)

<a id="9d1f73a8-fabd-493e-9003-0a36503c7573"></a>

読み手は、可変なグラフ(節点の状態が変わり、辺が増減する)を uniqnode に置きたい者と、
node/src/graph.rs を読む者。最初の利用者は lamalium の作業グラフで、つなぐ計画と両側の
決めごとは [docs/plan/LAMALIUM.md](#68571059-94ed-4aa2-8ae0-b2862d1de44e) にある。ここが
決めるのは、どのオブジェクトを書き、どの ref に束ね、どの口で操作するかだけである。

この層は意味を知らない。attrs の中身も、どの型が向きを持つかも、どの状態が終わりかも
呼び手のものである。知ると、呼び手の書式がこちらの仕様の一部になり、書式が変わるたびに
uniqnode の変更と再起動が要る。

## なぜこの形か

オブジェクトは不変(I1)で、作業の項目は状態が変わる。素朴に「節点 = kind:node」に
すると、状態を変えるたびに ID が変わり、その節点を指していた辺が古い版を指したままに
なる。可変な状態は ref 層だけに置く(I2)ので、1 つの節点を 3 つに分ける。

1. 恒等ノード。中身は名前だけで、二度と変わらない。その ID が節点の永久の身元である。
2. 状態ノード。属性の実体。更新のたびに新しい ID で、previous が前版を指す。
3. ref `graph/<グラフ>/nodes/<節点>`。現行の状態ノードを指す、唯一の可変状態。

辺は恒等ノードの ID を members に持つ(I7)。この 1 つの選択から、要るものがすべて出る。

- 節点をいくら更新しても辺は張り替えなくてよい。
- 辺 1 本が ref 1 本なので gc の根に入り([docs/design/GC.md](#9b1ceac3-f3cf-4595-87cb-6e40ce0900e5)
  の根は ref・pin・保持表明の和集合)、削除は tombstone で表せる。
- 版は previous の鎖で全部残る。旧版は現行 ref から辿れるので gc に消えない。
- 着地の時刻は ref レコードの at である。オブジェクトに時刻を入れない(入れると同じ
  attrs の再 PUT が別 ID になり、冪等が壊れる。doc_rev と同じ理由)。
- 複製がそのまま効く。ref も辺も既存のレプリケーション(SPEC §7.3)で運べる。

## オブジェクトの形

```jsonc
// 恒等ノード(不変・永久に同じ ID)
{"v":1,"kind":"node","contents":{"graph":"lamalium-plan","id":"n_verbatim_measure"}}

// 状態ノード(更新のたびに新しい ID。previous は初版だけキーなし)
{"v":1,"kind":"node","contents":{
  "identity":"s256:<恒等ノード>",
  "attrs":{ 呼び手の任意の c1 オブジェクト },
  "previous":"s256:<前版の状態ノード>"}}

// 型ノード(第一級。型の名前だけを持つ)
{"v":1,"kind":"node","contents":{"edge_type":"blocks"}}

// 辺。members の順が向きである
{"v":1,"kind":"edge","type":"s256:<型ノード>","members":["s256:<from>","s256:<to>"]}
```

attrs は c1 の値なので、c1 の制約がそのまま掛かる(SPEC §4.1): 浮動小数点は使えず、
整数は 64bit 符号付きの範囲、キーの重複は不正である。順位のような数は整数で書く。
大きさの上限は `graph::ATTRS_MAX_BYTES`(8 KiB)で、超えれば取り込む前に断る。計画文書の
本文の置き場ではない(本文は文書層のコレクションに置き、節点は anchor で指す)。

向きを持たない型を使いたいときは、呼び手が members の順を正規化して渡す。この層は
どの型が向きを持つかを知らないので、`serial/n_b/n_a` と `serial/n_a/n_b` は別の辺である。

## 名前

グラフ名・節点名・辺の型は、ASCII の英数字と `_` `-` `.` の 1..=64 字である
(`graph::is_valid_name` の 1 箇所。should/0135)。`/` と空白を含まないので ref のパスに
そのまま置け、`.` と `..` は道に見えるので断る。断りの文面も
`graph::invalid_name_refusal` の 1 箇所から出る(must/0023)。

節点名を 1 語に縛る必要はこの層には無い。縛りが要るのは文書層に置く形の方で、索引語の
切り方(ASCII の英数字と `_` の連なりが 1 語)のために `n-007` が `n` と `007` に割れる
([docs/design/SEARCH.md](#19574e78-9bf5-4f87-a4c2-c4a10222c580) の「索引語の切り方」)。
グラフ層は索引を通らないので、この歪みを受けない。

## 口

```
| Method | Path | 役割 |
|---|---|---|
| GET    | /v1/graphs                         | グラフ名の一覧(節点か辺を 1 つでも持つもの) |
| GET    | /v1/graphs/{g}                     | 全件(節点 + 辺)。描画はこの 1 本で足りる |
| PUT    | /v1/graphs/{g}/nodes/{n}           | 節点の作成と更新。本文が attrs のオブジェクト |
| GET    | /v1/graphs/{g}/nodes/{n}           | 現在の attrs・恒等 ID・状態 ID・seq・at |
| DELETE | /v1/graphs/{g}/nodes/{n}           | tombstone |
| GET    | /v1/graphs/{g}/nodes/{n}/history   | 版の一覧(新しい順。各版に attrs と at) |
| GET    | /v1/graphs/{g}/nodes/{n}/neighbors | 隣接。?direction=in|out|both・?type=<型> |
| GET    | /v1/graphs/{g}/edges               | 辺の一覧。?type=・?from=・?to= |
| PUT    | /v1/graphs/{g}/edges/{型}/{from}/{to} | 辺。本文は要らない |
| DELETE | /v1/graphs/{g}/edges/{型}/{from}/{to} | tombstone |
```

辺の名前を呼び手から受け取らないのは、名前と中身が食い違う形を作れないようにするため
である。名前が `<型>/<from>/<to>` そのものなので、同じ辺の再作成は必ず同じ ref に当たり、
冪等が名前から出る。

状態遷移に専用の口は無い。「着地済みにする」は attrs を変える PUT である。遷移の語彙を
この層が知らないので、知らないものに口を作れない。

節点の一覧・全件・隣接の順は決定的である(節点は名前順、辺は (型, from, to) 順。
should/0125)。同じグラフから毎回同じ HTML が出る。

読み口(`--listen-agent`)からは、`--agent-graph <g>`(読める)と
`--agent-graph-writable <g>`(書ける)で許したグラフだけが見える。どちらも与えなければ、
グラフ層は読み口に現れない。書ける名は読めもする(読み戻せない書き手を作らない)。
`GET /v1/graphs` は読み口の表に無い: 許していないグラフの名を知らせないためで、呼び手は
グラフを名指しする([docs/design/AGENT_DOOR.md](#02f79aec-2f12-41e6-bede-1557d4719e4d))。

## 冪等

- 同じ attrs の再 PUT は何も書かない。応答の `updated` が false、`seq` が null、
  `new_objects` が 0 でそう言う。比べるのは attrs であって状態ノードの ID ではない:
  previous があるため、同じ attrs でも版が違えば別の ID になる(doc_rev の
  (source, chunks 列)の比較と同じ理由。[docs/design/INGEST.md](#47d69a3e-c39a-4e76-9814-e9c24240293b))。
- 同じ辺の再作成も同じで、ref を触らない。
- 「ref が動いたか」を言う鍵の名は、PUT が `updated`、DELETE が `deleted` である。同じ問い
  なのに綴りが違うので、両方を 1 つの分岐で読む呼び手は取りこぼす(2026-09-09 に lamalium
  の client が実際に踏んだ: 削除は成功していたのに `updated` が無いことで断っていた)。
  揃えないのは、口が既に据わって呼び手が付いた後だからである。DELETE は成否も status で
  言う(消したら 200、元から無ければ 404 と `deleted` が false)ので、鍵を見るより status を
  見る方が短い。
- 書く順はオブジェクト(恒等 → 状態)→ ref である(set_ref は存在しない target を拒む。
  SPEC §5.3)。

## 断り

- 両端のどちらかがグラフに無い辺は 400 で断り、どちらが無いかを言う。名前だけの端を持つ
  辺が描画の入力に現れないようにするためである。
- 辺が付いたままの節点の DELETE は 400 で断り、どの辺かを並べる。黙って辺を宙に浮かせない
  (must/0022)。先に辺を消す。
- 在らぬ節点の GET と DELETE は 404 である。これはローカルな事実であって、不存在の言明では
  ない(SPEC §7.2)。
- 一覧の途中で状態ノードが読めなかった(ストアに無い・形が崩れた)ときは、飛ばさずに
  500 で断る。一覧は描画の入力であり、黙って欠けた一覧を渡すと、消えた項目と読めなかった
  項目が見分けられない。索引(導出データ)が壊れた 1 個を飛ばすのとは逆の判断である。

## 検索索引に触れないこと

グラフ層の書き込みは検索の見えを動かさない。検索索引の世代は collections/ 配下の ref の
束縛であり(取りこぼしが無い限りオブジェクト数を見ない。node/src/search.rs の Generation)、
`graph/` の ref も新しいオブジェクトも束縛を変えないからである。実装はこれに合わせて、
グラフの書き込みで索引の温めに合図を送らない。送ると 1 巡の書き込みが本番規模の作り直しを
起こす(2026-09-08 の実測で 31,232 チャンクの作り直しが 1 回 10.5 秒)。

裏返しに、グラフは検索で引けない。「X は何を待つか」は隣接の口で引くものであって、
検索で当てるものではない。

## 費用

一覧と隣接は、グラフの ref を一巡して状態ノードと辺を読む(節点数 + 辺数のオブジェクト
読み)。索引もキャッシュも持たない。45 節点 30 辺の規模では 1 桁ミリ秒で、300 節点でも
同じ桁である。汎用の逆引き索引(`GET /v1/objects/{id}/referrers`)を使わないのは、
それが全オブジェクトを解析する導出データで、世代がオブジェクト数だから書き込みのたびに
無効化されるためである(2026-09-08 の実測: 55,455 オブジェクトの冷えた構築が 15.07 秒、
2,694 オブジェクトで 63 ミリ秒)。グラフの大きさで決まる費用を、ストア全体の大きさで
払わない。

history は reflog を一巡して版 → 時刻の表を作る。描画の道ではなく、たまに引く道である。

## 意図的に持たないもの

- 状態の語彙・型の語彙・属性のスキーマ。呼び手のものである。
- 向きの正規化。どの型が向きを持つかを知らない。
- 部分グラフの深さ指定と、複数の書き込みを 1 本にまとめる口。要ると分かってから足す。
- グラフの描画。uniqnode は節点と辺を返すだけで、HTML は読み手が組む。viewer は検索専用の
  ままである([docs/design/VIEWER.md](#4cd4c71a-ecf3-44a8-a97b-bb2c8d8fe847))。
- 読み口への露出。許可表に載せるのは別の段である
  ([docs/design/AGENT_DOOR.md](#02f79aec-2f12-41e6-bede-1557d4719e4d))。今のところ
  グラフの口は主の口だけにある。
