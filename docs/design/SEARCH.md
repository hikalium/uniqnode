# SEARCH — 検索層(文字 bigram 転置索引・BM25・埋め込み・RRF 融合・POST /v1/search)

<a id="19574e78-9bf5-4f87-a4c2-c4a10222c580"></a>

読み手は、検索層のコード(node/src/search.rs、node/src/embed.rs と、node/src/api.rs の
/v1/search)を読む者と、この層の上にリランカーなどを足す者。順位の質を数値で測る側は
[docs/design/EVAL.md](#1109a04b-923e-4493-8f00-d704047d6a2a)、この層を LLM エージェントへ出す
アダプタは [docs/design/MCP.md](#dacd474d-424a-45d5-a278-766fc2465dd9) にある。この文書は
検索層の現在の実装を記述する。取り込み層
([docs/design/INGEST.md](#47d69a3e-c39a-4e76-9814-e9c24240293b))のチャンクと doc_rev の上に
載り、コア・プロトコル・ストレージ形式には手を入れていない。方式は 3 つある: 語の一致で引く
BM25、意味の近さで引く埋め込み、両者の順位を RRF で融合したハイブリッドである。BM25 は外部
依存を持たず、埋め込みだけが外部の埋め込みサーバに依存する(届かなければ BM25 に劣化して
答える)。fetch 側は既存の GET /v1/objects/{id} で足りるので、検索専用の取得 API は無い。
MCP の fetch ツールも別経路ではなく、同じ store の呼び出しに出典を添えるだけの薄い層である
([docs/design/MCP.md](#dacd474d-424a-45d5-a278-766fc2465dd9))。

## 索引語の切り方

- 文字列を索引語の列に切る実装は純関数 terms_of の一箇所にあり、索引の構築と問い合わせが
  共用する(should/0135)。チャンク 1 件がどの文字列からどれだけ索引語を出すかは、その上の
  純関数 chunk_terms_of の一箇所が決める(索引の構築と、評価ハーネスの対照方式が共用する)。
- 索引語はチャンクの本文と見出し(meta.breadcrumbs)の両方から採る。チャンカーは見出し行を
  本文に残さず meta.breadcrumbs へ写す
  ([docs/design/INGEST.md](#47d69a3e-c39a-4e76-9814-e9c24240293b) の「チャンク分割」)ので、
  見出しを含めなければ節の題だけにある語はどのチャンクからも消え、検索で到達できない。
- 見出しの語は本文の 2 回ぶんとして数える(定数 BREADCRUMB_WEIGHT)。重みは出現数を増やす
  形で与えるので、BM25 の tf と文書長の両方が同じ 1 本の語の列から出る(フィールドごとに
  別の長さを持つ仕掛けは無い)。重み 1(素直な連結)と、tf だけに重みを付けて文書長は
  見出しを 1 回ぶんで数える形の両方を評価ハーネス
  ([docs/design/EVAL.md](#1109a04b-923e-4493-8f00-d704047d6a2a))で測ったうえで、この形を
  採った。実測値は評価ハーネスのテスト(node/tests/eval.rs)のリテラルが持つ。
- 見出しは 1 段ずつ切る(段をつないでから切らない)。つなぐと段の境をまたぐ bigram が生まれ、
  どの見出しにも無い語が索引に入る。
- PDF のチャンクの meta.breadcrumbs は節見出しの経路である(node/src/outline.rs が
  しおりか語の高さから復元する。INGEST の「PDF 抽出」)。見出しの取れない文書だけが空になる。
- スニペットは本文の先頭のままで、見出しは混ぜない(見出しは応答の citation.breadcrumbs が
  持つ)。
- 全体を小文字化した上で、ASCII 英数字と `_` の連なりは 1 語まるごと 1 語にする。
  token_estimate のような識別子や英単語の完全一致のためで、`_` を語に含めるので識別子は
  途中で割れない。
- 非 ASCII の英数字(仮名・漢字など。判定は char::is_alphanumeric)の連なりは文字 bigram に
  する(「世代整合」は 世代・代整・整合)。連なりが 1 文字だけなら、その 1 文字を語にする。
- それ以外(空白・記号・句読点)は区切りで、語にならない。ASCII と非 ASCII の境界でも
  連なりは切れる。
- 1 文字の非 ASCII のクエリ語は、bigram の索引にそのままでは載らない(連なりの途中の文字は
  bigram の一部としてだけ現れる)ため、その文字を含む全索引語の位置表を統合した擬似語として
  検索する。同じチャンク内で文字が複数の bigram に現れるぶん出現数は重複して数えるが、
  順位付けにしか使わないので許す。

## 索引の構築と世代

- 転置索引は導出データ(I4)であり、Store::open では作らない(open はオブジェクトを
  パースせずハッシュだけを見る唯一の共有経路であり、そこに全件パースを足すと壊れた
  オブジェクト 1 個でストアが開かなくなる)。見えの全チャンクを一度走査して作り、以後は
  キャッシュ済みの索引で応える(逆引きの ReferrerIndex と同じ扱い)。作る判断は api.rs の
  with_current_index の一箇所にあり(古ければ作り直す。should/0135)、検索・全文取得・
  温めのどれもそこを通る。
- serve は要求を待たずに索引を温める(api.rs の start_index_warmer)。起動直後に裏の
  スレッドが 1 回作り、以後は書き込みの口(PUT documents・POST collections/{c}/fetch・
  POST /v1/objects・PUT /v1/refs・POST /v1/sync の受け取り)が書き終えるたびに合図を送り、
  スレッドが作り直す。続けて届いた合図は静穏(定数 INDEX_WARM_QUIET、1 秒)のあいだ
  1 回にまとめる(ディレクトリをまとめて取り込むとき、1 文書ごとに作り直さない)。
  作り直しはキャッシュのロックの中で行うので、作り直しの最中に来た検索は古い索引で答えず
  終わるのを待ち(入れた直後に引けないことを黙って起こさない。must/0022)、2 本の作り直しが
  同時に走ることも無い。作り直しのあいだストアのロックを持つのは要求が作るときと同じで、
  持つ時間は構築そのものの時間である。作り直すたびにログへ
  「search index built in <ms> ms (<chunks> chunks)」の 1 行を残す。実測(2026-09-06、
  55,452 オブジェクト・31,232 チャンク)では冷えた初回の検索が 22.46 秒、温まれば
  0.3〜0.7 秒である。ストアを直接開く mcp には温めが無く、初回の要求が作る。
- 埋め込みを装備した serve は、温めの後に続けて無いベクトルを裏で埋める(api.rs の
  start_vector_filler。「コーパスの埋め込みと serve の分担」)。契機は温めと同じ 1 本の合図で、
  温めのスレッドが温め終えるたびに補完のスレッドへ送る(いつ埋めるかの判断は温めの側の
  1 箇所)。温めと違い、検索は補完を待たない: 温めは秒単位で、待てば入れた直後の文書が
  引ける。補完は埋め込みサーバとの往復で分単位かかりうるうえ、穴があっても BM25 で答えられ、
  応答の degraded が穴を言う(should/0128)。待たせて得るものが無い。補完のスレッドを温めと
  別にするのも同じ理由で、温めのスレッドで続けて行うと、補完のあいだの書き込みの温めが
  その終わりまで待たされる。
- 世代は構築時点の (object_count, 署名者ごとの最終 seq) の組で、両方が現在値と一致する
  限り索引は最新である。object_count だけでは足りない: 既存 doc_rev への張り替え
  (巻き戻し)や tombstone は ref レコードしか増やさず、旧版のチャンクが索引に残る。世代が
  ずれたら次の要求で作り直す。
- 索引対象は「見え」だけ: collections/ 配下の非 tombstone ref が指す現行 doc_rev の
  チャンクのみ(既定の読み手は見えだけを読む。
  [docs/design/ASSERTIONS.md](#c05379e2-2d30-41bc-8342-62103d94bb21) の原理 5)。
  annotations/ などの ref は文書の見えではないので対象外。旧版・訂正済みの言明は ref から
  辿れないので索引に入らない。
- 無い(他ノードの ref の複製前)・UTF-8 でない・c1 でない・形の崩れたオブジェクトは
  飛ばす(索引は導出データであり、壊れた 1 個で構築全体を失敗させない)。語の無いチャンク
  はどのクエリにも一致しないので索引に入れない。

## BM25

- 得点は BM25 で、k1 = 1.2、b = 0.75(Okapi の慣用値)。idf は負にならない +1 の形
  ln(1 + (N - df + 0.5)/(df + 0.5)) で、全体は
  idf × tf(k1+1) / (tf + k1(1 - b + b·len/avg))。文書長 len はチャンクの語数、avg は
  索引済みチャンクの平均語数。数式の家は純関数 bm25_term_score の一箇所にある
  (should/0135)。
- クエリも terms_of で語に切り、重複を除いた各語の得点をチャンクごとに合算して降順に
  返す。collection を指定するとそのコレクションだけに絞る(df は索引全体で数える。順位は
  どちらでも同一応答内でのみ意味を持つ)。同点は索引順(ref 名の昇順 → chunks 列の順)で
  安定に決める(should/0125 の決定性)。
- 合算した得点には被覆率(そのチャンクが当たったクエリ語の数 ÷ クエリの異なり語の数)を
  掛ける(古典的な coord)。当たった語が稀だというだけで、問いの一部にしか当たっていない
  チャンクを上位に置かないためである。文字 bigram の索引ではこの歪みが日本語の複合語で
  顕著に出る: 「割り込み」と「取り込み」は bigram を 2 つ共有し、英語コーパスの中では
  日本語 bigram の df が 1 なので idf が跳ね上がる
  ([docs/analysis/20260817-japanese-partial-match.md](#ff9299d5-3dfb-4ad0-9b3b-f5d597271cdc))。

## 埋め込み(意味検索)

- ベクトルの計算は自前で持たず、OpenAI 互換の /v1/embeddings を話す埋め込みサーバへ HTTP で
  委譲する。手元の既定は llama-server + bge-m3(FP16)で、エンドポイントは定数
  DEFAULT_EMBEDDING_URL(http://127.0.0.1:8083/v1/embeddings)、模型識別子は
  DEFAULT_EMBEDDER_ID("bge-m3")、次元は DEFAULT_EMBEDDING_DIMENSION(1024)。serve と embed の
  --embed <url> でエンドポイントを、--embedder <id> で識別子を替える。
- 要求は {"input": [文字列…], "model": embedder_id} で、1 要求に載せる本数は
  DEFAULT_EMBED_BATCH(16)。応答は data の各要素の index と embedding を読み、index で並べ直す
  (応答の並び順に依存しない)。次元が違う・数でない要素がある・index が重複または欠けるといった
  応答は通さず、何が食い違ったのかを言って失敗する(must/0022)。
- ベクトルは受け取った側で L2 正規化する(純関数 normalized の一箇所。should/0135)。正規化して
  あれば内積がそのままコサインになる。bge-m3 の応答は正規化済みだが、それを前提にせずここで
  揃える。
- 得点は全走査のコサインである。ANN は持たない: 実データ規模の 25k チャンク・1024 次元の f32 は
  約 100MB で、RAM に載せて総当たりできる。
- 模型の同一性は embedder_id が担う。サーバ側の申告では確かめられないことが実測で分かっている:
  llama-server の GET /v1/models の capabilities は、埋め込み専用に起動していても
  ["completion"] を返すので埋め込み対応の判定に使えず、埋め込み応答の model 欄は要求に書いた
  文字列のこだま(要求が省いたときだけ自分の重みのパス)なので、どの模型が計算したかを証明
  しない。したがってサーバの生存確認も、capabilities を読むのではなく実際に 1 本埋め込んで
  みることで行う(should/0116)。
- ベクトルはビット単位の再現性を持たない。同じ入力でもバッチの構成が変わると 1e-4 級でずれる
  (GPU の畳み込み順序)ので、バイト一致を同一性の判定に使わない。同一視の鍵はあくまで
  (チャンク ID, embedder_id)である。

## ベクトルの置き場

- ベクトルは導出データ(I4)であり、真実の源泉には入れない。オブジェクトにも reflog にも書かず、
  <data_dir>/derived/embeddings/<embedder_id>.vec に置く(場所を決める家は VectorCache::path_for
  の一箇所)。消して失われるのは計算時間だけで、同じチャンクと同じ模型から同じ鍵で作り直せる。
  fsck の対象でもない(fsck が見るのは真実の源泉の側である)。
- 鍵は(チャンクのオブジェクト ID, embedder_id)。ID は内容ハッシュなので、文書を改版しても
  変わっていないチャンクのベクトルはそのまま効き、二つの文書が同じ本文のチャンクを持てば
  ベクトルは 1 本で共有される。embedder_id は鍵の半分であると同時にファイル名でもあるので、
  模型を替えたベクトルは別のファイルに並び、混ざらない(識別子に使える文字を英数字と - _ . に
  限るのはこのためである)。
- ファイルは追記のみである。先頭は 1 行の見出し「uniqnode-vectors 1 <embedder_id> <次元>」で、
  読み込み時に照合し、模型か次元の食い違うファイルは黙って混ぜずに断る。以降は 1 レコードずつ、
  u16 の ID 長・ID のバイト列・f32 の並び・payload(ID とベクトル)の CRC32 が続く(いずれも
  リトルエンディアン)。
- 追記はまとまりごとに fsync する。途中で止めてもそこまでの計算は残り、続きから再開できる
  (25k チャンクの計算を最初からやり直さないため)。
- 追記の途中で止まった末尾は壊れて見える。読み手はレコードが読めなくなった時点で読むのをやめ、
  そこまでを使い、捨てた末尾のバイト数を数えて持つ。導出データなので捨ててよいが、捨てたことは
  黙らず、ログに何バイト捨てたかを出す(must/0022)。捨てた末尾を持つキャッシュへの次の追記は、
  読めた所まで切り詰めてから足す。壊れた記録の後ろに足すと、読み手はそこで読むのをやめるので
  足した記録が永久に見えず、serve の裏の補完が同じチャンクを毎回埋め直してファイルだけが
  伸びる。

## コーパスの埋め込みと serve の分担

- コーパス側の埋め込みは「見えのチャンクのうちベクトルの無いものを集める」(embed.rs の
  collect_missing。ストアを読むだけ)と「集めたものを埋め込んでキャッシュに足す」
  (embed_missing。埋め込みサーバとの往復)の二段で、入口が二つある。どちらも同じ二つの関数を
  呼ぶ(should/0135)。
  - 埋め込みを装備した serve は、起動直後と書き込みの後(索引の温めと同じ合図)に裏で埋める
    (EmbeddingService::fill_missing)。ストアのロックを持つのは集める走査のあいだだけで、往復は
    ロックを離してから行う(往復は分単位かかりうる。その間も検索と書き込みは通る。問いの
    埋め込みをロックの外で済ませるのと同じ規律)。走査と往復のあいだに書き込みが入っても混ざら
    ない: 鍵は内容ハッシュなので、消えたチャンクのベクトルは無駄になるだけで、増えたチャンクは
    次の合図が拾う。同時に 2 本は走らず、走っている間に届いた合図は終わってからもう 1 回に
    まとまる。埋めたらログに「embedded <n> missing vectors in <ms> ms (<cached>/<distinct> cached)」
    の 1 行を残す。埋められなければ(埋め込みサーバが落ちている・届かない)理由を 1 行残して
    次の合図を待つが、直前と同じ理由なら繰り返さない(読み口の束縛の再試行と同じ規律。理由が
    変わればまた記す)。その間の検索は BM25 に劣化して答え、degraded が理由を言う。
  - CLI の uniqnode embed <dir> は同じことをストアを独占して行い、何件が既にあって何件を新しく
    計算したかを報告する。ストアを開くので serve 停止中のストア用である(ingest や sync と同じ
    扱い。ストアは二重に開けない)。ストアを直接開く形の mcp には補完が無いので、そちらは
    これで埋める。
- serve の検索要求が埋め込むのは問い合わせの文だけである。コーパスのベクトルはキャッシュ
  ファイルを読むだけなので、検索要求が模型の計算を待つことはない(裏の補完も待たない。「索引の
  構築と世代」)。埋め込みを装備するのは --embed を明示したときだけで、起動時に相手の生存は
  確かめない(should/0114)。
- 帰結として、文書を取り込んだ直後から補完が終わるまでのあいだ、新しいチャンクにはベクトルが
  無い。意味検索の対象から漏れ、応答は被覆の欠落を degraded で言う(「ベクトルは <n>/<全>
  チャンクぶんしかない」)。補完が終わると、次の検索から欠落は消える。
- ベクトルが増えてもストアの世代は動かない。補完も uniqnode embed もストアに何も書かないから
  である。そこで serve 側のベクトル索引は、ストアの世代に加えてキャッシュファイルの見かけ
  (大きさと最終更新)を見て、作り直すかどうかを決める(EmbeddingService::index_is_current)。

## RRF 融合

- 融合は Reciprocal Rank Fusion である。各方式が返した順位 r(1 始まり)に 1/(k + r) を与えて
  足し、降順に並べる(定数 RRF_K = 20)。得点ではなく順位だけを使うので、BM25 の得点と
  コサインを較正する必要がない。ノードをまたぐ統合でも同じ性質が効く(SPEC §7.1 の kind:search)。
- 融合に持ち込む深さは、要求の top_k と定数 RRF_DEPTH(30)の大きい方である。
- 深さと k は実データ 34 問で 12 組の格子を測って選んだ(実測 2026-08-18。
  [docs/analysis/20260818-search-quality.md](#4b5e913a-5a50-4633-9ecb-b65afc24fc8a))。深さ 30・
  k 20 が最良か同値で、深さ 10 のときは k を 10/20/60 と振っても順位が 1 件も動かない(k は
  深さを広げて初めて測れる)。深さ 50・100 では遠い順位の凡庸な候補が両方式に現れて上がり、
  かえって落ちる。評価ハーネスの固定コーパス(23 チャンク)は 12 組すべてが同値で、深さと k を
  そこでは選べない。慣用値の k = 60 を外したのは、原典が数千件の完全な順位列を融合する設定で
  選んだ値であり、数十件だけを融合するこの形では順位 1 位と 10 位の重みの差が 15% しか残らない
  ためである。
- 融合する単位はチャンクの位置である。BM25 の索引とベクトルの索引は同じ走査(見えのチャンクを
  同じ順に辿る)から作るので位置が揃う。揃っていなければ融合せず、劣化して BM25 で答える。
- 語の一致の側は、被覆率が定数 MIN_FUSION_COVERAGE(0.5)に満たなければ融合に入れない。
  得点を下げるだけでは足りない: RRF は順位しか見ないので、問いの一部にしか当たっていない
  1 件でも「BM25 の 1 位」として意味検索の 1 位と同じ重みを持ち、先頭を争ってしまう。
  外したときは degraded がそう言う。境目は実データへの問い 11 本で測って置いた: 英語の
  問いは 2 語でも 12 語でも被覆 0.90〜1.00、日本語の部分一致は 0.25〜0.33 で、谷はその
  あいだにある([docs/analysis/20260817-japanese-partial-match.md](#ff9299d5-3dfb-4ad0-9b3b-f5d597271cdc))。
  方式に bm25 を明示した要求には掛けない(語の一致そのものを求めている呼び手には、当たった
  通りを返す)。
- 被覆は語のまとまり単位で数える(純関数 term_groups_of)。ASCII の 1 語は 1 まとまりで、
  当たれば 1.0。非 ASCII の連なりは、そこから出た文字 bigram 全部で 1 まとまりになり、
  当たった割合がその値になる。まとまりごとの平均が被覆率である。この区別が要るのは、
  まるごとの語の一致(意図が当たった)と断片の一致(当たっていない)を同じ物差しで測る
  ためである: カタカナの問いを英語へ広げると、広げた語 1 個の一致で被覆は 0.5 に届き、
  「割り込み」が「取り込み」に当たる型の断片一致は 0.33 のままで届かない。平坦に数えて
  いたころは、広げた語の一致が日本語 bigram に薄められて融合から外れていた
  ([docs/analysis/20260818-search-quality.md](#4b5e913a-5a50-4633-9ecb-b65afc24fc8a))。
- BM25 が 1 件も返さなかったときは、融合の入力が片側だけになり、返る列は埋め込み単独と同じに
  なる。方式は hybrid のままだが(融合は要求どおり走っている)、degraded に「BM25 が 1 語も
  一致せず、順位は埋め込み単独と同じである」と書く。実データでは純日本語の問い 14 本すべてで
  これが起きていて、応答からは融合が効いているように見えていた(実測 2026-08-17。
  [docs/analysis/20260817-real-corpus-search-quality.md](#faeda9ac-5e9e-4091-8122-2fba9f80c8db))。
  片肺であることは、順位の意味を読む側にとって「劣化」と同じ重さの事実である。

## カタカナの問いを英語の術語へ広げる

- 語の一致に渡す問いだけを広げる(node/src/translit.rs)。カタカナ → ローマ字 → 母音を捨てた
  子音の骨格 → 索引に実在する語との照合、という道で英語の術語を足す。`sukurachipado` と
  `scratchpad` がどちらも `skrSpd` になるので、挿入母音の分だけ離れた綴りが結びつく。
- 候補にするのは索引に実在する語だけである(架空の綴りを作らない)。骨格が同じ語が複数ある
  ときは、出現の多い語を先に採る(綴りの近さより先に見ると、当たりが 32/70 から 53/70 に
  増えた。コーパスには OCR の断片が混じっていて、綴りだけでは `buffer` より `buff` が近い)。
- 意味検索の側には広げた語を渡さない。多言語の模型は日本語の問いをそのまま扱えるので、
  英語の語を混ぜるとかえって問いの意味が薄まる。
- 複合語を分割しない(`scratchpad` を `scratch` + `pad` にしない)のは測って決めた。どちらも
  実在する語だが df が高く idf が低いので、`pad` を含むだけの紙面が上がり、正解が 1 位から
  9 位へ落ちる。2 語綴りしか無いコーパスでは、まるごとで当たらないときだけ分割に落ちる。
- 届く率の実測: 仕様書 27 本の索引(語彙 77,376)に対し 70 語中 53 語。日本語だけで BM25 が
  0 件だった 50 語のうち、広げた後は 50 語すべてに当たりが出て、42 語は英語で問うたときと
  同じチャンクが 1 位になった([docs/analysis/20260818-search-quality.md](#4b5e913a-5a50-4633-9ecb-b65afc24fc8a))。
- 届かない型も分かっている。骨格が 2 子音の語は原理的に分けられない(`bt` = bit/byte/but)。
  語形変化は区別しない(controller と control は同じ骨格)。英語の綴りが不規則な語
  (scheduler・queue)には届かない。漢字の訳語(割り込み → interrupt)は音ではなく意味の
  対応なので、この層の外である(扱えるふりをせず何も返さない)。

## 低情報チャンクの後処理

- 目次の紙面・柱(ページヘッダ)だけ・ページ番号だけのチャンクは、順位付けのあとで応答から
  落とす。判定は純関数 is_low_information の一箇所にあり、索引の構築時に 1 回だけ走って
  チャンクごとの真偽を索引が持つ(応答のたびに全文を持ち歩かないため。索引済みチャンクが
  持つ本文はスニペットだけである)。
- 判定は三つのどれかに当たることである: 本文に占める `.` の割合が 0.15 を超える(目次の
  点線)、4 個以上の `.` が連なる行が 3 本以上ある、本文が 300 文字未満で異なり索引語が
  8 語未満である。語の数え方は索引と同じ terms_of を通すので、日本語の短い本文は文字 bigram の
  ぶん語数が足りて残る。
- 落とすのは応答であって索引ではない。索引から外すと、pdftotext が柱しか採れなかった図版の
  ページが GET /v1/objects/{id} の引用ごと見えなくなる。後処理なら、要求に
  include_low_information を立てれば同じ問いで戻ってくる。
- 落とした件数は応答の filtered_low_information と標準エラーの 1 行が持つ。黙って捨てない
  (must/0019 と同じ理由: 落とした結果は、落としたと言わなければ最初から無かったことと
  区別できない)。落としたぶん結果は top_k より短くなる。順位付けそのものには手を入れない
  ので、融合の深さ(RRF_DEPTH)も動かない。
- 実データ(仕様書 PDF 25 本・25,098 チャンク)では 1,960 件(7.8%)がこの判定に当たり、
  上位 10 件への混入は英語の問いで 2.9〜3.6%、純日本語の問いで 10.7% だった。標本 20 件の
  目視で本文のチャンクは含まれず、検証済みの正解ページ 54 チャンクのうち巻き込みは 1 件
  (見出しだけの断片)である。順位そのものへの効きは小さいが、一度も悪化しなかった
  ([docs/analysis/20260817-real-corpus-search-quality.md](#faeda9ac-5e9e-4091-8122-2fba9f80c8db))。

## POST /v1/search

```jsonc
// 要求。collection(省略時は全コレクション)・top_k(省略時 10、1..=1000)・method・
// include_low_information(省略時 false)・full(省略時 false)は省略可。
// query は空でない文字列で、索引語を最低 1 語含む(含まなければ 400)。
{ "query": "世代の整合", "collection": "notes", "top_k": 10, "method": "hybrid",
  "include_low_information": false, "full": false }

// 応答。results は score 降順。citation の page は PDF のチャンクだけが持つ。
// degraded は、要求した方式で答えられなかったときだけ載る。
// filtered_low_information は、低情報として落とした件数(0 なら載らない)。
// text は要求が full: true のときだけ載る(チャンクの全文)。
{ "degraded": "埋め込みサーバが設定されていない(serve の --embed)",
  "filtered_low_information": 2,
  "method": "bm25",
  "results": [
    { "citation": { "at": 1786904557, "breadcrumbs": ["分散設計", "世代の整合"],
        "collection": "notes", "document": "search_ja", "position": 1 },
      "id": "s256:…", "score": 2.94, "snippet": "転置索引は導出データであり…",
      "source_url": "/v1/objects/s256:…/rendition/source",
      "text": "転置索引は導出データであり、遅延構築である。…" } ],
  "score_semantics": "bm25" }
```

- snippet はチャンク本文の先頭 200 文字(定数 SNIPPET_CHAR_LIMIT。文字境界で切る)。
  全文は id(チャンクのオブジェクト ID)から既存の GET /v1/objects/{id} で取るか、
  要求に full: true を付けて各件の text として受け取る。
- full: true のとき、各件にチャンクの全文が text として載る(鍵は辞書順なので snippet・
  source_url・text の順)。full の無い要求の応答は従来のままで、text の鍵そのものが無い。
  全文は索引に無い(索引が持つのは抜粋だけ)ので、run_search が求められた件だけストアから
  引く。索引にある ID がストアにチャンクとして無ければ抜粋だけにせず 500 で言う
  (must/0022)。full のとき top_k は定数 FULL_TOP_K_LIMIT(10)までで、超えれば 400
  「top_k は full のとき 1..=10」(検証は parse_search_request の一箇所)。全文 1 件は
  抜粋の数倍あり、読み手は LLM の文脈だからである。分散検索でピアから来た件には
  載らない(ピアの答えは抜粋しか運ばない。source_url と同じ扱い)。MCP の search ツールは
  この欄を使わず、全文は fetch で取る。
- source_url は原本(このチャンクの出た文書そのもの)を取る道である。写しの恒等レシピ
  ([docs/design/RENDITION.md](#6046eeca-1d95-4d47-87da-13f86c7710dc))の URL で、HTML なら
  紙面 1 枚、PDF ならまるごと、markdown なら原文が返る。抜粋の周りを読むには文書へ行く道が
  要るのに、これまでは写しの目録をもう一度引かないと分からず、読み手によって道があったり
  無かったりしていた(ビューワは上位の数件しか目録を引かず、MCP は引かない)。恒等レシピは
  何も生成しないので、道の有無は要求の前に決まる: doc_rev に source のある件にだけ載り、
  無い件では欄そのものが出ない(空文字を作らない)。分散検索で他のDBノードから来た件にも
  載らない。そのチャンクは相手のストアにあり、こちらの URL では取れないからである。
- citation は取り込み層の引用規則([docs/design/INGEST.md](#47d69a3e-c39a-4e76-9814-e9c24240293b)
  の「文書モデル」の節)のとおり: collection はコレクション名、document は ref パスから
  collections/<コレクション名>/ を除いた残り、position は chunks 列の添字、breadcrumbs は
  見出しの入れ子パス、PDF はさらに page。collection を載せるのは、全コレクションを跨いで
  検索したとき、どの束から来た件なのかが応答だけで読めるようにするためである(MCP の
  アダプタは「<コレクション名>/<文書名>」と描く)。
- citation の at は取得日時である。その版を見えに置いた署名付き ref レコードの時刻(SPEC §4.4)
  を unix 秒で載せる。その版がこのノードに取り込まれた時刻であって、原典が書かれた時刻ではない。
  引用の組み立ては Citation::of の一箇所にあり、REST も MCP も同じ値を出す(引用を二重に実装
  しない。should/0135)。日時としての描画は読み手の側の仕事で、MCP のアダプタは UTC で描く。
- method は "bm25"(語の一致)・"embedding"(意味の近さ)・"hybrid"(両者の RRF 融合)の
  どれか。省略時の既定は装備と top_k で決まる(決め方の家は default_method): serve に
  --embed が無ければ bm25、あれば top_k が定数 EMBEDDING_ONLY_TOP_K(3)以下で embedding、
  それより多ければ hybrid である。方式の指定を知らない呼び手が、埋め込みを備えた節点で
  黙って語の一致だけに取り残されないためであり、境目を置くのは、浅い打ち切りと深い打ち切りで
  どちらの方式が上かが入れ替わるからである。実データの 14 主題 × 3 通りの言い方で測ると、
  3 通りの平均は Recall@3 が埋め込み単独(0.738 対 0.691)、Recall@5 と Recall@10 が融合
  (0.809 対 0.833、0.905 対 0.929)で、交差点は k=3 と k=5 のあいだにある(実測 2026-08-17。
  [docs/analysis/20260817-real-corpus-search-quality.md](#faeda9ac-5e9e-4091-8122-2fba9f80c8db))。
  少ししか返さない要求は 1 位を外すと取り返せず、たくさん返す要求は読み手が下位まで見られる。
- include_low_information を true にすると、低情報チャンクの後処理を止めて順位のまま返す
  (省略時は false で落とす)。図版のページのように pdftotext が柱しか採れなかったチャンクを
  探すときに使う。
- 応答の method は実際に使った方式である。要求した方式で答えられなかったときは、method が
  落ちた先を指し、degraded がその理由の文を持つ。同じことを標準エラーにも書く(黙って劣化
  しない。should/0128)。劣化の理由は、埋め込みサーバに届かない・serve に --embed が無い・
  ベクトルが 1 件も無い・キャッシュを読めない・ベクトルの索引が BM25 の索引と揃っていない、
  である。方式を落とさない二つの理由も同じ degraded に載る: 被覆の欠落(ベクトルが一部の
  チャンクにしか無い)と、片肺の融合(hybrid で BM25 が 1 件も一致しなかった)である。
  両方が同時に当たれば、二つの文が「。」でつながって載る。
- filtered_low_information は、順位には入っていたが低情報として応答から落とした件数である
  (0 なら載らない)。同じことを標準エラーにも書く。
- score_semantics は方式ごとに "bm25"(BM25 の得点)・"cosine"・"rrf"(順位から作った得点)。
  どれもスコアが同一応答内の順位付けにだけ意味を持つという意味論であり、応答をまたいだ比較や
  絶対値の閾値には使えない。
- クエリの埋め込みは、どのロックも取る前に済ませる。埋め込みサーバとの往復を待つあいだ store の
  ロックを持つと、検索 1 本で API 全体が塞がるためである(sync のロックの規律と同じ理由)。
  クエリ 1 本ぶんの期限は 15 秒。
- 応答本文は score のためだけに手組みの JSON である。score は小数で、c1 は整数しか持たない
  ため。citation は小数を持たないので c1 の正規形をそのまま埋める(書き手は citation_value の
  一箇所)。読む側は小数を読める最小の JSON(node/src/json.rs。埋め込みサーバの応答を読むのと
  同じ一箇所)を通り、SearchResults に組み直す家は parse_search_response である。書き手と読み手を
  api.rs の同じ節に並べて置き、噛み合うことを単体試験 rest_search_bodies_survive_a_round_trip が
  確かめる(should/0135)。

## GET /v1/objects/{id}/citation

```jsonc
// 見えにあるチャンクの出典。見えに無い ID・チャンクでない ID・持っていない ID は null。
{ "citation": { "at": 1786904557, "breadcrumbs": ["分散設計", "世代の整合"],
    "collection": "notes", "document": "search_ja", "position": 1 } }
```

- 全文そのものは既存の GET /v1/objects/{id} が生のバイト列で返す。こちらは出典だけを返す。
  引用の組み立ては検索と同じ索引(Citation::of)から行うので、search が示した出典と一致する。
- 逆引き(GET /v1/objects/{id}/referrers)と同じく、これは「自分の見えの範囲」の導出データで
  ある。null は不在の言明ではない(SPEC §7.2/§10)。
- この口を足したのは、走っている serve へ転送する形の MCP
  ([docs/design/MCP.md](#dacd474d-424a-45d5-a278-766fc2465dd9))が、fetch の応答に出典を添える
  ためである。転送する形はストアを開かないので、出典を組めるのは serve だけである。

## 既知の癖

- 索引の構築は 25k チャンク規模で約 9 秒かかる。serve は起動直後と書き込みの後に裏で
  作るので(「索引の構築と世代」)、要求がそれを待つのは作り直しの最中に来たときだけで
  ある。ストアを直接開く mcp では初回の検索が構築込みで応答する。
- コーパス全体の埋め込みは時間で買う。実データ(25,098 チャンク)の全件で 936 秒、毎秒およそ
  27 チャンクだった。キャッシュは 104,596,198 バイトになり、2 回目の uniqnode embed は 9.8 秒で
  再計算ゼロ、fsck も 0 エラーだった(実測 2026-08-17)。serve の裏の補完は取り込んだぶんだけを
  埋めるので、取り込みのたびに払うのは新しいチャンクの数に比例した時間と、無いものを集める
  走査(索引の構築と同じ全走査。その間ストアのロックを持つ)である。
- 意味検索は直接的な問いに的確に効く。同じストアでの実測 2026-08-17:
  「SYSCALL instruction description」の 1 位は sdm_vol2 の 1414 ページ(SYSCALL の説明そのもの)、
  「how does the processor enter system management mode」の 1 位は SMM の定義だった。日本語の
  「システムコール命令の説明」でも同じ 1414 ページが 2 位に入り、言語をまたぐ検索が実データでも
  効くことが確かめられている。
- 目次ページ(点線だけの行)や見出しだけの短いチャンクが上位に紛れる癖は、意味検索でも残る。
  BM25 について知られていた癖であり、埋め込みはそれを解消していない。原因は調べていない
  (短いチャンクのベクトルが一般的な向きを向きやすいためと推測できるが、測っていない)。
  順位を作り直すのではなく、上の「低情報チャンクの後処理」で応答から落とす形で対処している。
- 問いの当たり方は、言語ではなく「文書が使う語がクエリにあるかどうか」で決まる。同じ 14 主題を
  純日本語で問うと MRR 0.332、日本語の文に英語の術語を混ぜると 0.869、英語だけなら 0.705〜0.798
  である(実測 2026-08-17。
  [docs/analysis/20260817-real-corpus-search-quality.md](#faeda9ac-5e9e-4091-8122-2fba9f80c8db))。
  語順どおりの直訳(「モデル固有レジスタ」)は当たり、文書に一度も出ない訳語(「高精度イベント
  タイマ」)は届かない。この事実は検索の内側では直せないので、呼び手への指示として MCP の
  ツール説明([docs/design/MCP.md](#dacd474d-424a-45d5-a278-766fc2465dd9))に書いてある。
- これらの癖は評価ハーネスの固定コーパスの数値には出ない。合成の小コーパス(23 チャンク)は
  目次の紙面も柱だけの紙面も持たず、同じ判定に掛けても低情報チャンクは 0 件である。順位品質の
  較正は評価ハーネス([docs/design/EVAL.md](#1109a04b-923e-4493-8f00-d704047d6a2a))の領分だが、
  実データの癖を捕まえる対はまだ無い。

## 順位の取り直し(cross-encoder リランカー)

<a id="6df75ea0-ad86-460a-be04-29660201a7fb"></a>

- serve(と、ストアを直接開く形の mcp。組み立ては同じ関数 reranker_from を通る)に
  `--rerank <url>` を与えたときだけ装備する(既定では動かない)。問いと本文の組を
  そのまま模型に読ませて採点し直す層で、実装は node/src/rerank.rs にある。手元の既定は
  llama-server + bge-reranker-v2-m3(FP16、VRAM 1.1 GB)。転送する形の mcp・viewer・embed は
  装備する口を持たないので、この引数を受けたら起動時に断る
  ([docs/design/MCP.md](#dacd474d-424a-45d5-a278-766fc2465dd9))。
- 採点し直すのは融合の上位 DEFAULT_RERANK_DEPTH(30)件で、送るのは索引が持つ抜粋(200 文字)
  である。同じ問いで抜粋と全文を較べたところ上位の並びが一致したので、全文を取りに行く往復を
  足していない。抜粋に節見出しの経路を前置してから送る(その紙面が何の節かを模型に見せる)。
- 取り直した順位は、一次検索の順位を置き換えるのではなく RRF で融合する。同じ 34 問で両方を
  測ると、融合が R@3 0.941 対 0.853、R@5 1.000 対 0.853、MRR 0.747 対 0.699 で上回る。差の
  中身は「置き換えは取りこぼす」ことで、置き換えると 2 問が上位 10 件から完全に落ち、1 問が
  1 位から 9 位へ下がった。片方の判断だけに委ねたときの失敗の幅が大きい。
- 得点の意味は変わる。取り直したときの score_semantics は "reranker-logit" ではなく融合の
  得点(順位から作った値)であり、同一応答内の順位付けにしか使えない性質は変わらない。
- 判定の基準(EVAL (uuid:72106edc-2c58-44d3-91c6-7b2a3dd7dfda))で読むと、この層は良い方に
  倒れる。取りこぼしは装備してもしなくても 35 問中 0 件のままで、10 件の中の集まり方が上がる
  (Recall@5 0.941 → 1.000、Recall@3 0.882 → 0.941)。Recall@1 は 0.647 → 0.559 と下がるが、
  1 位を当てることは採否の材料にしない。
- それでも既定では装備しない。理由は順位の質ではなく費用である: 外部の模型(VRAM 1.1 GB)と
  1 要求あたり 0.8 秒を足すのに、取りこぼしは減らない(既に 0 件である)。上位への集まりを
  買いたい運用者が `--rerank` で選ぶ
  ([docs/analysis/20260818-search-quality.md](#4b5e913a-5a50-4633-9ecb-b65afc24fc8a))。
- 届かないときは黙って劣化しない。順位は取り直す前のまま答え、理由を degraded に足す。
  装備していないこと自体は劣化ではない(呼び手は取り直しを要求できないので、無い装備の
  不在を毎回の応答で詫びる理由が無い)。
