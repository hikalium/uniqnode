# RENDITION — ページの写し(遅延生成してストアに足す・レシピを ref の名前に畳む)

<a id="6046eeca-1d95-4d47-87da-13f86c7710dc"></a>

読み手は、写しのコード(node/src/rendition.rs と、node/src/api.rs の `/rendition`)を読む者と、
ブラウザや LLM から PDF の紙面を見たい者。検索そのものは
[docs/design/SEARCH.md](#19574e78-9bf5-4f87-a4c2-c4a10222c580)、取り込みは
[docs/design/INGEST.md](#47d69a3e-c39a-4e76-9814-e9c24240293b)、画面は
[docs/design/VIEWER.md](#4cd4c71a-ecf3-44a8-a97b-bb2c8d8fe847) にある。

検索が返すのは pdftotext が抜いた本文のチャンクである。それは読むための正典だが、図表や
組版は落ちている。この層は、そのチャンクと同じ紙面を「見る」ための写し(ページ画像・その
ページだけの PDF・原本そのもの)を出す。

## 何を出すか

チャンクの ID から、その紙面について取れるものを並べる。

| 別名 | 中身 | 型 | 実測(sdm_vol2 1414 ページ目) |
|---|---|---|---|
| source | 原本そのもの(PDF・HTML・素文) | 中身で決まる | 0.03 秒・生成しない |
| thumb | 一覧用のサムネ | image/jpeg | 0.21 秒・70 KB |
| page | 拡大用の紙面 | image/png | 0.48 秒・371 KB |
| pagepdf | そのページだけの PDF | application/pdf | 0.17 秒・65 KB |

- `source` は恒等レシピである。何も描かず、doc_rev の `source` が指す原本 blob をそのまま
  返す。ブラウザは `#page=N` の断片でその紙面を開くので、写しを 1 バイトも作らずに
  「原本の当該ページ」へ辿れる。poppler の無いノードでも動く唯一の道でもある。
- `pagepdf` は `pdftocairo -pdf` の再描画である。`pdfseparate` は共有資源を丸ごと複製する
  ので採らない(同じページで 2.69 秒・25.5 MB。pdftocairo は 0.06 秒・65 KB。実測)。
  再描画なので字形の写しは完全ではない(実測で em ダッシュが落ちた)。正典の本文は
  取り込み済みのチャンクであって、この PDF のテキスト層ではない。応答の note がそう言う。

## いつ作るか

要求されたときだけである。取り込み時に一括生成しない。手元の実データは PDF 34 本・のべ
14,565 ページで、全ページを全レシピで作れば 7 GB 級になる(実測 2026-08-18)。見られる紙面は
その一部である。

手順は三段で、ストアの錠を握ったまま poppler を回さない(埋め込みと同期に同じ規律が
ある)。

1. 錠を取り、鍵(原本 blob・ページ・レシピ)から ref を引く。有ればそれを返して終わり。
   無ければ原本のバイト列と、ページ番号の照合に使う本文を持ち出す。
2. 錠を放して poppler を回し、ページ番号を照合する。
3. 錠を取り直して `put_object` と `set_ref`。待っているあいだに他のスレッドが同じ鍵を
   入れていたら、そちらを使って自分の産物は捨てる(content-addressed なので同じ ID に
   なるはずで、違えばログに出す)。

生成中も他の要求が通ることは、統合試験 the_api_stays_open_while_a_rendition_is_being_made が
実プロセスで確かめる(錠を持ったまま呼ぶ形に戻すと落ちる)。

## 導出データをストアに入れる条件

写しは導出データである。それでも `<data_dir>/derived/` ではなくストアのオブジェクトにする。
I4(導出データを真実の源泉に入れない)の禁止は「再導出できないものを入れない」ための
規律であり、作り方が添えてあれば言明として扱える、という線引きを採った。

条件は「レシピが揃っていること」である。ref の名前が作り方そのものを持つ。

```
renditions/<原本blobのオブジェクトID>/<ページ番号>/<道具>-<版>-<形式>[-<品質>]-<寸法>-<色>
  → 写しのオブジェクトID
```

- 名前を付けずに写しを入れる道は存在しない。入口は「レシピから名前を組んで put して
  set_ref する」1 本だけで、レシピの欠けた画像は入れないという規律は、規律ではなく
  不可能性である。
- 鍵は文書名ではなく原本 blob の ID である。同じ PDF を別の名前で取り込んでも写しは共有
  され、文書名を変えても無効化されない。
- 許すレシピは表に固定する。任意の寸法を受けない: ストアが永久である以上、口の広さが
  そのまま容量の広さになる。
- 画像は PNG/JPEG の生バイト列そのままで、c1 で包まない(新しい kind を作らない・base64 で
  膨らませない)。オブジェクトの中に説明を混ぜないのは、混ぜるとバイト列がレンダラの出力と
  違うものになり、「同じレシピで同じ ID になるか」を確かめられなくなるからである。
- 決定性は実測した: pdftoppm も pdftocairo も同じ入力から 3 回とも同一バイトを返す。ただし
  それに寄りかからない。ベクトルのキャッシュと同じく鍵で引く(値の内容ハッシュで
  同一視しない)ので、環境が違って別のバイト列が出ても、鍵の下に新しい版が並ぶだけである。
- ref の名前に `s256:` のコロンをそのまま入れる。set_ref・再オープン・fsck を通ることは
  実測で確かめた(名前を削る変換を挟むと、URL へ写すときの取り違えが生まれる)。

## ページ番号の照合(黙って間違えないために)

チャンクの `meta.page` は pdftotext の改頁の数え、poppler の `-f/-l` は物理ページ番号である。
整合するはずだが、ずれれば「間違っているのに正しく見える」写しが出る。引用としては最悪の
壊れ方なので、既定で照合する。

- 生成した紙面(画像なら原本の同じページ)に pdftotext を掛け、見えにあるその紙面の
  チャンク本文と 5 語の連なりの重なりを測る。閾値 0.5、最良のチャンクで判定する。
- 食い違ったら `put_object` も `set_ref` もせず、原本 ID・ページ・レシピ・重なりの数値・
  両方の本文の抜粋を並べて失敗する。
- チャンクが 1 件も無い紙面(図版だけのページ)は証拠が無いので止めない。
- 照合の材料は検索索引から引く。索引はチャンクごとに原本 ID とページ番号を RAM に持って
  いるので、同じ紙面のチャンク(平均 1.8 件)だけを読めば足りる。見えを走査して集める道も
  残してあるが(索引を持たない CLI 用)、大きな仕様書では桁が違う: sdm_vol2(4,188
  チャンク)で走査は 5.4 秒、索引からなら 0.21 秒である(実測)。

## 口

```
GET /v1/objects/{チャンクID}/rendition          -> application/json(目録。生成しない)
GET /v1/objects/{チャンクID}/rendition/{別名}   -> レシピが決める型(無ければ作って返す)
```

目録は席ごとに `state` を持つ: `stored`(ストアに有る)・`absent`(頼めば作る)・
`unavailable`(作れない。必ず `reason` を添える)。PDF 由来でないチャンクには `source` の
席だけを出す。出せないものの席は作らない。

誤りは「誰が直せるか」で分ける: 400 は要求の組み立て(知らない別名・PDF でない文書)、
404 は見えに無いチャンクや持っていない blob、503 は poppler が無い(導入手順つき)、
500 は描画の失敗(poppler の言い分を引用)。

既存の `GET /v1/objects/{id}` は 1 バイトも変えていない(生のバイト列を octet-stream で
返す口のまま)。`source` の型だけは中身で決める: 許可表の application/pdf を無条件に
名乗ると、markdown の原文を PDF だと嘘をつくためである。判定は 4 通りで、`%PDF-` で
始まれば application/pdf、頭が `<!doctype html` か `<html` なら text/html、ほかの UTF-8 は
text/plain、UTF-8 でなければ octet-stream になる。HTML を text/plain で返すと紙面が札のまま
出てしまうので、HTML と名乗れる原本だけ text/html にする。外部を参照しない 1 枚として
取り込んだ紙面([docs/design/INGEST.md](#47d69a3e-c39a-4e76-9814-e9c24240293b) の HTML 抽出)は、
この道でそのままブラウザに出せる。

HTML の原本だけは `Content-Security-Policy: sandbox allow-scripts` を添えて返す(serve も、
それを写すビューワも)。取り込んだ紙面はよそから来た文書であって、この生成元の `/v1/*` を
叩ける権限を渡してよいものではない。`allow-same-origin` は与えないので紙面は不透明な生成元で
描かれ、スクリプトだけは動く(保存した紙面を、保存したときの姿で見せるため)。ビューワ自身の
頁には印を付けない。自分の生成元の `/v1/*` を叩けないと検索が動かないからである。

## 既知の癖

- ページの写しは消せない。ref を tombstone すれば見えからは消えるが、バイト列は pack に
  残る(pack GC が未実装。[docs/plan/RAG.md](#86363f4a-3df6-4aa2-9c64-b99aa5cb4e7b))。
  遅延生成なので「実際に見た紙面だけ」に収まるが、増える一方であることは変わらない。
- `renditions/` は伝播交換にそのまま載る。写しを他ノードへ配りたくない運用のための輸出
  除外は、まだ入れていない([docs/plan/RAG.md](#4ed764d8-a570-4809-bd0c-80de0d4b5545))。
- `thumb` のレシピ名にある `gray` は「灰色を指示した」であって「灰色になった」ではない。
  poppler 22.02.0 の jpeg 出力では `-gray` が効かない(有無で出力バイト列が完全に一致。
  実測)。レシピ名は再導出の指示なので、指示は残してある。
- MCP は写しを作らせない(読むだけ)。模型は画像を読めず、生成させれば消せないオブジェクトが
  無制限に増える。生成の引き金はビューワだけが引く。
