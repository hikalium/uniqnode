# INGEST — 取り込み(チャンキング・文書モデル・PDF・注釈)と訂正表現の実装計画

<a id="11ff6fec-cf85-4ae9-a24c-6098964f6cce"></a>

読み手はこの作業単位を実装する者。[docs/plan/RAG.md](#2e00cbd1-45df-4b4f-8b47-c0b57c298f9e) の
取り込みの項と [docs/plan/RAG.md](#bf3ef713-3971-403a-88e7-93bc647db29c) の訂正のグラフ表現の
項を、着手できる具体度まで確定するのがこの文書の仕事である。

目的は二つで、分けられない。手元の文書群(Markdown・プレーンテキスト・PDF)を取り込んで
各チャンクの引用元を引ける状態にすることと、取り込んだ言明の誤りを追加の言明として
訂正できるようにすること。後者を分けられないのは、訂正の発行経路が注釈取り込みの検証機構を
そのまま使うからである(訂正の段を参照)。BM25 検索
([docs/plan/RAG.md](#35a888f7-5ac6-4333-831c-dd7753b82315) の項)はこの計画に含めない。

この計画で「言明」と呼ぶのは、グラフに置かれた個々の不変オブジェクトを指す。ここで扱うのは
主に注釈の辺(annotates 型)だが、訂正の members には任意のオブジェクト ID を置ける。

## 前提と依存

  [docs/plan/RAG.md](#2e00cbd1-45df-4b4f-8b47-c0b57c298f9e) の冒頭が持つ。本計画が実際に

  見なす。SPEC §4.3)だけで、コア・プロトコル・ストレージ形式には変更を加えない。上位層

  os_dev_specs_private の index.txt にある。
- data.md の実形式(パーサはこの形だけを受け付ける。must/0020): spec_id の見出し + 表題・

  刷り番号 138、sdm_vol2 の p.317 の刷り面は「Vol. 2A 3-217」で通し番号ですらない)。
  2026-08-16 の照合もこの番号空間で行った。meta.page も同じ番号空間で書く。

  注釈は 100 件で、2026-08-16 に全件を PDF の現行版と照合済み。内訳は機械照合 99 件 +
  手動確認 1 件(「CPUID list」。個人ラベルのため紙面見出しと機械的には一致しない)。

## この計画で確定する判断

### 文書モデル(上位層 kind)

blob(原文そのもの)・chunk(検索と引用の単位)・doc_rev(版)・ref(現在の見え)の4層。

```jsonc
// chunk: 引用に必要な文脈を自身で持つ
{ "v": 1, "kind": "chunk", "text": "…",
  "meta": { "breadcrumbs": ["5 …", "5.2.3.2 …"], "page": 162 } }

// doc_rev: 原文 blob と順序付きチャンク列を束ねる版
{ "v": 1, "kind": "doc_rev", "source": "s256:<blob>",
  "chunks": ["s256:…", "s256:…"],
  "meta": { "name": "acpi_6_4", "media": "pdf", "extractor": "pdftotext 22.02" },
  "previous": "s256:<前版の doc_rev>" }   // 初版は previous キーなし
```

- 文書名は取り込み起点からの相対パスから拡張子を除いたもの(acpi_6_4.pdf なら acpi_6_4)。
  種別の判定は入力ファイル名の拡張子で行い、拡張子を ref 名には残さない。
- ref `collections/<コレクション名>/<文書名>` が現行の doc_rev を指す。文書一覧は既存の
  refs 一覧(GET /v1/refs)で足りるので、新しい一覧 API は作らない。
- 引用は doc_rev 側から組み立てる: 文書名は ref パスから `collections/<コレクション名>/` を
  除いた残り、文書内位置は chunks 列の添字、見出しは meta.breadcrumbs、PDF はさらに
  meta.page。チャンク単体から出発する逆方向(このチャンクはどの文書のものか)は、訂正の段で
  作る逆引き索引が与える。
- チャンクの順序は doc_rev の chunks 列だけが持つ(順序は辺が持つ、という I7 と同じ形)。
  chunk 自身に番号を持たせず、順序という一つの事実を二箇所に置かない。
- doc_rev に時刻を入れない。入れると同一内容の再取り込みが別 ID になり、べき等(I1)が
  壊れる。取り込み時刻は ref レコードの at(可変層・署名付き)が既に持っている。
  不変データと可変メタデータの分離(I4)の帰結。
- 再取り込みの同一性は doc_rev の ID ではなく (source, chunks 列) の一致で判定する。previous
  キーがあるため、同じ入力でも素直に組むと毎回別 ID の doc_rev ができてしまい、自ら課した
  no-op が壊れる。一致した場合は新しい doc_rev を作らず ref も触らない。
- 捨てた代替案: chunk が本文を持たず blob へのオフセット参照だけを持つ形。保存の重複は
  減るが、引用とスニペット返却のたびに blob の取得と切り出しが要る。同一本文のチャンクは
  content-addressing が重複排除する(効くのは再取り込みと文書内の繰り返し。改版をまたいで
  page や breadcrumbs が変われば別の言明になり、排除しないのが意図)。重複の実コストは
  測っていないので、書き込み経路の段で総オブジェクト数と総保存量を一度記録する。

### チャンキング規則

- 大きさは上限 480 の近似トークン数。根拠は検索スニペットとして一度に読める長さで、
  埋め込みの入力長は 480 に対して桁違いに大きいため制約になっていない。評価ハーネス
  ([docs/plan/RAG.md](#8912f7c0-05fd-464d-9cba-4db8a5d30527) の項)で測って調整する暫定値
  である。
- 近似トークン数は「ASCII 文字は 1/4 トークン、非 ASCII 文字は 1 トークン」の重み付き
  文字数とする。純関数 token_estimate として一箇所に置き、チャンカーとテストが共用する
  (should/0135)。注釈の照合で数える「語」(注釈の照合の節)とは別物であり、別の関数に
  なる。
- Markdown: 見出し境界を優先し、段落単位で上限まで詰める。見出しの入れ子パスを各チャンクの
  meta.breadcrumbs に写す。
- PDF: pdftotext の form feed をページ境界として保存し、ページをまたぐチャンクを作らない
  (引用のページ番号を一意にするため)。ページ内は段落単位で詰める。form feed は最終ページの
  後ろにも付く(実測: 3 ページの抽出で 3 個)ので、素直に分割すると末尾に空ページが生まれ、
  ページ番号が 1 つずれる。末尾の空区画は捨てる。
- プレーンテキスト: 空行区切りの段落単位で詰める。
- 捨てた代替案: 正確なトークナイザの導入。依存ゼロ方針と衝突するうえ、チャンク境界の質は
  評価ハーネスで測って調整するほうが確実。

### PDF 抽出

- pdftotext は Command で直接起動する(シェルを経由しない。must/0009 と同じ理由)。
  実行ファイルは引数 --pdftotext <path> の明示指定を優先し、無指定なら PATH を引く。
  見つからないときは、必要なバイナリ名と導入手順(前提節)を示して明示的に失敗する。
  黙って PDF を飛ばさない(must/0022 の同型)。
- doc_rev.meta.extractor に抽出器の名前と版を記録する。poppler の版が変わると抽出テキストが
  揺れうるが、blob は PDF そのものなので、再抽出の差は新しい doc_rev になるだけで、旧
  doc_rev は旧抽出についての真のまま残る(I1)。

### 注釈索引の取り込み

- data.md を前提節の実形式で読み、注釈 1 件を annotates 型の辺として取り込む:

```jsonc
{ "v": 1, "kind": "edge", "type": "s256:<annotates 型ノード>",
  "members": ["s256:<節タイトルのノード>", "s256:<PDF blob>"],
  "meta": { "page": 162 } }
```

- 参照先は文書名ではなく PDF blob のハッシュ(I1)。spec_id から blob への解決は、先に
  取り込み済みの PDF の ref(`collections/<コレクション名>/<spec_id>`)を引いて
  doc_rev.source を使う。したがって注釈の取り込みは PDF の取り込みの後になる。ref が無い
  spec_id に当たったら、その注釈を飛ばさず取り込み全体を失敗させ、先に PDF を取り込むよう
  促す(must/0022 の同型)。
- PDF の版が変われば新しい blob になり、旧注釈は旧版についての真のまま残る。data.md の
  ページずれは可変な名前(sdm_vol3)に注釈を張ったことの帰結であり、この規律が事故クラス
  そのものを消す。
- 注釈の辺・検証記録・訂正の辺は、コレクションごとの索引に束ねて ref `annotations/<コレク
  ション名>` から指す。これらは doc_rev の到達閉包に入らないので、索引の ref が無いと複製や
  pin の対象にならず、根拠だけが取り残される。索引は取り込みの実行ごとにまとめて作り直す
  (1 件ごとに作り直さない)。索引は注釈数に比例して大きくなるので、100 件規模を超えて
  常用するなら分割が要る。今回の規模では分割しない。
- 型ノード(annotates / corrects / supersedes)の c1 本文は定数として一箇所に定義し、生成側と
  判定側が同じ定数を使う(must/0023)。

### 注釈の照合

- 取り込み時に注釈タイトルと当該ページ本文を照合し、不一致は取り込まずに報告する。
- 照合規則(2026-08-16 の data.md 検証で用いたトークン照合を、ここで規範として定める):
  小文字化して英数字以外で分割し、数字だけの語を除いたうえで、タイトル側の語の 6 割以上が
  当該ページ本文の語の集合に含まれれば一致とする。
- 一致に使った本文行は根拠として検証記録に残す(訂正の表現の節)。
- 照合は一つの関数に置き、取り込み時の検証と、訂正のための再検証が共用する(should/0135)。
- 閾値 6 割の正確さは結果に効かないと見ている。実データでは正しいページはタイトルの語を
  ほぼ全部含み、含まない側は現在 1 件(CPUID list)しかない。したがって内訳が変わらない
  閾値の幅(安全窓)が存在するはずで、6 割はその内側という想定である。これは注釈の段の
  受け入れで実測して確かめる。
- 機械照合で一致しないが人が正しいと確認した注釈(前提節の 1 件)は、method を manual と
  した検証記録を付けて取り込める。黙った例外は作らず、記録が残る形だけを許す。

### 訂正の表現

```jsonc
// 検証記録: 照合の方法と根拠を残すノード
{ "v": 1, "kind": "node",
  "contents": { "method": "token-match", "evidence": ["CPUID—CPU Identification"] } }
// method は token-match(機械照合)または manual(人手確認)

// corrects 型の辺: 誤りの訂正
{ "v": 1, "kind": "edge", "type": "s256:<corrects 型ノード>",
  "members": ["s256:<新しい言明>", "s256:<誤った言明>"],
  "meta": { "reason": "…", "verification": "s256:<検証記録>" } }
```

- corrects 型の辺: members は [新しい言明, 誤った言明] の順。meta.reason に理由、
  meta.verification に検証記録の ID を置く。meta 内の s256: 文字列も参照なので(SPEC §4.3)、
  到達閉包が根拠ごと運ばれる。
- 検証記録は「何を検証したか」を持たず、「どう検証し何を根拠にしたか」だけを持つ。検証記録
  から言明へ参照を張ると、注釈の辺の閉包に根拠が入らないうえ、逆向きに張って言明の meta に
  検証記録を入れると、抽出器の版が変わって根拠行が変わるたびに注釈そのものが別の言明に
  なってしまう。検証は言明についての別の言明であり、言明の同一性には混ぜない。
- 訂正の対象になる誤った言明は、照合で弾かれた注釈ではない(それはストアに入らない)。
  対象は既にストアにある言明で、出どころは三つ: 照合を通ったが誤っているもの(照合は
  「そのページにその語が載っている」ことしか言わない必要条件である)、ピアから伝播交換で
  届いた他ノードの言明、検証機構を入れる前に取り込んだもの。
- supersedes 型の辺: 文書の新版に伴う張り替え。members の順序は corrects と同じく
  [新しい言明, 旧い言明]。誤りの訂正とは別の型として区別する(旧言明は旧 blob について
  真のままであり、誤りだったわけではない)。doc_rev.previous が同名文書の版の連なりを自動で
  持つのに対し、supersedes は注釈のような個別の言明の追随を明示に張る。本計画で実装するのは
  型定数の定義までで、発行経路は改版追随が実際に必要になったときに足す。
- 現在の見えは ref が決める。検索と RAG が既定で使うのは ref の指す doc_rev に載った現行
  言明だけで、旧言明と訂正の辺は履歴として辿れる。
- 逆引き(あるオブジェクトを参照する既知オブジェクトの一覧)を導出データ(I4)として持つ。
  参照抽出は既存の collect_references を使う(should/0135)。これにより「この言明への訂正は
  あるか」が、旧言明しか持たない DBノードでも問える。

## 作業手順(段は名前で参照する。各段に確認方法を付す)

1. チャンカーの段。node/src/ingest.rs に token_estimate とチャンカー(Markdown・プレーン
   テキスト・ページ分割)を純関数で実装する。
   確認: ユニットテスト(境界・meta.breadcrumbs・同一入力から同一チャンク列)。token_estimate
   自体のテストは期待値をリテラルで書く(検査対象から期待値を導出しない)。
2. 書き込み経路の段。blob + chunk 群 + doc_rev + ref を一括で書く関数を ingest.rs に置く。
   順序は blob と chunk 群 → doc_rev → ref(set_ref は存在しない target を拒否するので ref は
   最後)。再取り込みの no-op 判定は取り込み経路が現行 ref を読んで (source, chunks 列) を
   比較して行い、一致すれば doc_rev を作らず set_ref も呼ばない(set_ref 自体は変更しない。
   既存の set_ref は同一 target でも新レコードを追記する)。
   確認: 再取り込みで ID 集合と ref の seq が変わらないこと(べき等 = I1 の検証)。あわせて
   投入後の総オブジェクト数と総保存量を一度記録する(重複コストの主張の裏づけ)。
3. 取り込み口の段。CLI `uniqnode ingest <data_dir> <コレクション名> <パス>`(ディレクトリは
   再帰)と API `PUT /v1/collections/{collection}/documents/{name}`(本文 = 生バイト列)。
   対象の拡張子は .md / .markdown / .txt / .pdf のみとし、それ以外は取り込まず、対象外の
   一覧を最後に印字する(黙って消さない)。CLI は排他ロックのため serve 停止中のストア用で
   あり、usage にその旨を明記する(serve 中は PUT API を使う。既存 sync サブコマンドと同じ
   扱い)。
   確認: 統合テストで、取り込んだ Markdown について ref から doc_rev、chunks の添字と
   辿り、文書名・位置・見出しの三つが揃った引用を組めること。実プロセスに生 HTTP/1.1 で
   当てる(should/0138)。CLI は実プロセスで起動する。引用を組み立てる専用 API は作らない。
4. PDF の段。pdftotext 委譲とページ対応チャンキング。
   確認: 複数ページの最小 PDF をテスト資材(ソースとは別ファイル。should/0112)に置き、
   先頭チャンクの meta.page が 1、最終チャンクの meta.page が総ページ数に一致し、末尾に
   空チャンクが生まれないこと。pdftotext 不在の環境ではテストを黙って飛ばさず、導入手順を
   示して失敗する([docs/design/TESTING.md](#267326f7-e919-48f2-9737-fe0c0daec9d5) の外部
   コマンドの規約に従う)。
5. 注釈の段。CLI `uniqnode ingest-annotations <data_dir> <コレクション名> <data.md のパス>`
   に data.md パーサ・照合・annotates 辺の発行・索引 ref の更新を実装する。人手確認済みの
   注釈は承認リストのファイルを `--manual <パス>`(spec_id とページの並び)で渡し、method を
   manual とした検証記録を付ける。型ノード三種の定数もこの段で定義する。
   確認: cargo test には data.md の抜粋と、照合に落ちる資材を置き(いずれもソースとは別
   ファイル。should/0112)、一致は入り不一致は取り込まず報告することを両向きに確認する
   (発火を一度も見ていない検証器は未検証なので、負例を必ず含める)。型定数は ID を固定した
   テストで押さえ、生成側と判定側が同じ定数を通ることを一つのテストで見る(must/0023)。
   前提節の全注釈の実投入は private な資材に依存するため、自動テストではなく完了条件の手動
   受け入れとして行う。受け入れの際、注釈ごとの一致率の分布を印字し、内訳が変わらない閾値の
   幅を求めて docs/analysis/ に記録する(新規文書は H1 直下に UUID アンカーを置く。
   must/0013)。幅が求まらず 6 割の付近で内訳が動くなら、閾値を決め直して判断の根拠を同じ
   記録に残し、取り込み済みの分を再検証する。
6. 訂正の段。CLI `uniqnode correct <data_dir> <誤った言明ID> <新しい言明ID> <理由>` が
   新しい言明を再照合して検証記録を作り、corrects 辺を発行して索引 ref を更新する。逆引き
   索引と GET /v1/objects/{id}/referrers を実装する。逆引きは遅延構築とし、Store::open には
   触れない(open は現在オブジェクトをパースせずハッシュだけを見る唯一の共有経路であり、
   ここに全件パースを足すと、壊れたオブジェクト 1 個でストアが開かなくなる)。パースできない
   オブジェクトは参照ゼロとして飛ばす。
   確認: 照合を通る注釈資材を先に取り込み、それを誤りとして訂正して corrects 辺を発行し、
   referrers で旧言明側から訂正が見つかること。あわせて既存の統合テスト一式が緑のままで
   あることと、逆引きの構築がストアの起動を遅くしていないことを見る。

順序の理由: チャンカー・書き込み経路・取り込み口の三段は Markdown だけで完了条件の前半を
満たす最短列。PDF の段と注釈の段はその上に載り、訂正の段は注釈の段の検証機構を前提にする。

## リスクと戻し方

- 大半は追加であり、既存のコア(kind の解釈・プロトコル・ストレージ形式)に変更はない。
  途中で失敗しても既存機能は壊れない。
- 例外は訂正の段の逆引き索引で、これだけが既存の起動経路に触れうる。遅延構築にして
  Store::open を変えないことでこれを避ける(訂正の段を参照)。壊れた場合の戻し方は索引の
  無効化であり、referrers が使えなくなるだけで取り込み済みのデータには影響しない。
- 取り込みの取り消しは ref の tombstone(既存機能)で現在の見えから外せる。参照されない
  オブジェクトは無害に残り、物理回収は pack GC
  ([docs/plan/RAG.md](#4ed764d8-a570-4809-bd0c-80de0d4b5545) の項)の領分。
- pdftotext の版差で抽出が揺れる危険は、doc_rev.meta.extractor の記録と content-addressing
  (PDF 抽出の節)で吸収する。
