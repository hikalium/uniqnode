# RAG: LLM から使える検索ストレージへ

<a id="86363f4a-3df6-4aa2-9c64-b99aa5cb4e7b"></a>

現在の状態: SPEC の適合レベル L0〜L4(単一ノードストア・レプリケーション・分散クエリ・
レプリカ健全性・グループ鍵)をすべて実装済み。テスト81本、CLI + HTTP API。
ゴールは、このシステムを RAG ストレージとして LLM エージェントから常用できる状態に
すること。以下は実行順に並べた作業項目(1〜5 がゴール達成の最短経路)。

## 1. 取り込み(チャンキングと文書モデル)

SPEC §9 の chunk / doc_rev を規範化して実装する。固定長(400〜512トークン相当を文字数で
近似)+ 見出しパンくずのメタデータ、blob + chunk + doc_rev(順序付き辺)+ ref。
CLI `ingest` と `PUT /v1/collections/{c}/documents/{name}`。
完了条件: Markdown ディレクトリを一括投入でき、同一内容の再投入が no-op(べき等 = I1 の
検証)で、チャンクから引用元(文書名・文書内位置・見出し)が引ける。

PDF 対応もここに含める:

- テキスト抽出は pdftotext(poppler)への外部プロセス委譲(llama-server・curl と同じ枠。
  sudo なしで `apt-get download` + ローカル展開により導入できることは確認済み)。
- ページ境界を保存したチャンキング(pdftotext の form feed 区切り)。引用は
  「spec_id + PDFページ番号 + 節」の形で返す。
- 注釈索引(os_dev_specs の data.md 形式: spec_id / URL / SHA-1 / ページ→節タイトル)を
  読み、トピック→(文書 blob, ページ)の辺として取り込む。取り込み時に、注釈タイトルと
  当該ページ本文の一致検証(2026-08-16 に data.md の検証で使ったトークン照合)を行い、
  不一致は取り込まずに報告する。
- 重要: 注釈辺の参照先は文書名ではなく文書 blob のハッシュとする(I1)。PDF の版が
  変われば新しい blob になり、旧注釈は「旧版についての真」のまま残る。data.md で起きた
  ページずれは、可変な名前(sdm_vol3)に注釈を張ったことの帰結であり、content-addressing が
  この事故クラスそのものを消す。
- 完了条件: os_dev_specs_private の PDF 25本 + 修正済み注釈 100 件が投入でき、検索結果の
  引用に PDF ページ番号が出る。

## 1b. リンクデータの訂正のグラフ表現(項目1と同時に設計を固定する)

注釈のようなリンクデータに誤りが見つかったとき、オブジェクトは不変なので「直す」ことは
できない。訂正は追加の言明として表現する:

- 訂正辺: `{kind:"edge", type:<corrects型ノード>, members:[<新しい言明>, <誤った言明>],
  meta:{reason}}`。検証の方法と根拠(照合ツール・根拠行)も検証記録オブジェクトにして
  訂正辺から参照する。訂正も署名付きの言明なので、誰が・なぜ直したかが残り、
  相反する訂正が共存できる(開世界)。
- 改版追随辺: 文書の新版に伴う張り替えは誤りの訂正ではない(旧言明は旧 blob について
  真のまま)。これは type:<supersedes型ノード> の別種の辺で表し、認識論的に区別する。
- 現在の見えは ref が決める: コレクションの doc_rev には現行の言明だけを載せ、検索・RAG は
  既定でそれを使う。旧言明・訂正辺は履歴として辿れる(doc_rev.prev と訂正辺の両方から)。
- 逆引き索引(あるオブジェクトを member に含む辺の一覧)を導出データ(I4)として持つ。
  これにより「この言明への訂正はあるか?」が、旧言明しか持たないノードでも
  ネットワークに問える(content-addressed なので問いが明確に定義できる)。

完了条件: 項目1の注釈取り込みで検証不一致が出た場合に、この形で訂正辺を発行できる。

## 2. BM25 検索(外部依存ゼロで検索可能にする)

文字 bigram の転置索引(導出データ。起動時にチャンク走査で再構築)+ BM25 +
`POST /v1/search`(snippet + ID + score + citation + score_semantics を返す)。
fetch 側は既存の `GET /v1/objects/{id}`。これだけでキーワード RAG として使える。
完了条件: 日本語・英語のクエリで該当チャンクが top-k に入り、識別子(関数名など)の
完全一致検索が効く。

## 3. 評価ハーネス

固定の小コーパスと「クエリ → 正解チャンク」対で Recall@k / MRR を `cargo test` の
回帰テストにする。以後の改善(埋め込み・融合・チャンク境界)の判断基準線。
実コーパス(自分のノート)での評価セット作成は運用作業として別途行う。
完了条件: 検索方式を切り替えて数値が比較できる。

## 4. 埋め込みとハイブリッド検索

llama-server(`/v1/embeddings`、bge-m3 想定)への HTTP クライアント。ベクトルは
(chunk, embedder_id) キーの導出層(全走査コサイン。RAM に載る規模では ANN 不要)。
BM25 と RRF で融合。llama-server に届かないときは BM25 のみに劣化して動き続ける。
完了条件: 言い換えクエリで意味検索が効き、評価ハーネスで BM25 単独より Recall@k が
上がることを数値で確認。

## 5. MCP アダプタ

search / fetch の2ツールを公開する stdio モード(`--mcp`)。コアはあくまで REST で、
MCP は薄い被せ物(rag_plan の設計判断)。
完了条件: Claude Code に登録し、エージェントが出典(引用元+取得日時)付きで回答できる。
ここで「LLM から使える RAG ストレージ」が成立する。

## 6. 分散検索(kind: search)

QUERY メッセージ署名(要求者の認証)と応答側の trust_level フィルタを入れた上で、
検索クエリを登録ピアへ散布し、各ノードのローカル top-k を RRF で統合する
(順位ベースなのでノード間のスコア較正が不要)。
完了条件: SPEC §7.1 の kind:search が動き、2ノードに分かれた知識が1クエリで返る。

## 7. 運用の仕上げ

systemd unit の例、バックアップ手順(封印セグメントの rsync + 復元検証)、README の運用節。
完了条件: 常用ノードが systemd で動き、バックアップからの復元手順が一度実証されている。

## 8. pack GC(機会層 evict の物理回収)

pack の書き直しで evict 済みオブジェクトのディスクを回収し、その上で min_replicas=0 の
LRU+参照カウント evict(SPEC §5.4)を有効化する。容量の小さいノードを本格運用する前提。

## 9. 失効文とグループ設定の伝播交換への載せ替え

現状は groups.json への手動配置。署名済み文書なので伝播交換に載せる素地はある。

## 10. その先

Web スナップショット(rag_plan の W トラック)、mgcanvas 形式エクスポートによる可視化、
Contextual Retrieval・リランカーなどの検索品質向上(評価ハーネスで測りながら)。
