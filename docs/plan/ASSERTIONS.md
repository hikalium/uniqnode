# ASSERTIONS — 言明・検証・訂正の論理設計

<a id="c05379e2-2d30-41bc-8342-62103d94bb21"></a>

読み手は、取り込みと訂正の実装計画([docs/plan/INGEST.md](#11ff6fec-cf85-4ae9-a24c-6098964f6cce))を
実装またはレビューする者と、将来この取り込み・言明の層の上に検索・埋め込み・LLM の層を
足す者。この文書の仕事は、実装計画の個々の決定(kind の形、meta に何を入れるか、参照の
向き、ref の使い方)が従う論理設計を、実装の詳細(CLI・API・ファイル配置・外部ツール)から
独立に固定することである。原理は六つで、中心は原理 4(真理の層の分離)にある。

実装決定の正典は実装計画、原理の正典は本文書である。実装計画は判断の現場で根拠を短く
再掲してよいが、根拠が原理と食い違ったら本文書の側が優先し、検収の手続き(末尾)で
どちらかを直す。原理の番号は安定識別子として扱い、原理を廃止しても番号は再利用しない
(SPEC の不変条件 I1〜I7 と同じ扱い)。

位置づけ: 取り込み層は未実装なので、must/0013(docs の design/plan 分割規則)の分類では
本文書も plan/ に置く。実装が着地したら docs/design/ へ移す(コードに直接は現れないが
実装の基礎方向を成す概念、という design/ の区分に入る)。移す際は、この位置づけの段落と
末尾の検収の節を現在の状態の記述に書き直す(そのまま移すと design/ に偽の記述が残る。
must/0010)。

## 原理 1(追加のみ): 変化は言明の追加だけで表す

- 言明とは、内容から ID が決まる不変オブジェクトである(SPEC の不変条件 I1)。この層が
  導入する言明は、チャンク(この文脈にこの本文がある)、doc_rev(この版はこの原文と
  このチャンク列から成る)、注釈(この blob のページ p は節 T を含む)、検証記録、
  訂正の辺、追随の辺。
- 言明は書き換えも削除もできない。世界の変化は二種類しかない: 新しい言明の追加と、
  見え(ref)の張り替え。
- 帰結: 「誤りを直す」という操作は存在しない。あるのは、誤りだと主張する新しい言明を
  足し、見えを新しい側へ張り替えることだけである。

## 原理 2(主張と運用の分離): ID に入るものが主張、入らないものが運用

- 言明の ID は内容の全体から決まる。だから「内容に何を含めるか」の決定は「その言明が
  何を主張するか」の決定そのものである。
- 主張の一部であるもの: チャンクの本文・見出しの文脈・ページ番号。どれが変わっても
  別の主張である。
- 主張の一部でないもの(これが運用): いつ取り込んだか(時刻)、誰がいまそれを現行と
  見なすか(見え)、どれだけ複製されているか(健全性)。これらは署名付きレコード
  (ref・pin・保持表明)の側が持つ(I2: 可変な状態は ref 層だけに置く)。
- 帰結 1: 内容が入力だけから決まる言明は、同じ入力から同じ ID しか生まれない(べき等)。
  時刻を内容に入れた瞬間にこれが壊れる。版の連なり(doc_rev の previous)のように過去の
  見えを内容に含める言明では、同一性の比較を内容の入力由来の部分で行うことでこの帰結を
  回復する(実装計画の同一性判定がその適用)。
- 帰結 2: 検証は主張の一部ではない。検証を言明の内容に混ぜると、検証のやり直し
  (根拠行の変化)が言明の同一性を変えてしまう。真理の主張と、その主張への信頼の根拠は、
  別のオブジェクトに分ける(原理 4)。

## 原理 3(参照は所有の宣言): 参照の向きは「いっしょに運ぶ」の宣言である

- 参照(s256:)は前方にだけ辿られ、到達閉包が複製・保持の単位になる(参照の規約は
  SPEC §4.3、到達閉包は SPEC §7.3)。したがって「A が B を参照する」と書くことは
  「A を運ぶ者は B も運ぶ」と宣言することである。
- 参照するには参照先の ID を知る必要があり、ID は内容が確定した後にしか存在しない。
  だから参照は常に作成済みのオブジェクトへ向かい、作成の順序が参照グラフに位相順序を
  与える。循環を作るにはハッシュの不動点を見つける必要があり、実際上できない。ゆえに
  参照グラフは有向非循環であり、閉包は常に有限に閉じる。
- 帰結 1: 訂正の辺は新旧の言明と検証記録を参照する。訂正を受け取った者は、根拠と
  旧言明ごと受け取る。
- 帰結 2: 逆向きの知識(この言明を参照するものは何か)は言明にできない。それは「いま
  自分が知っている言明の集合」に相対的な事実であり、集合が増えるたびに変わる。だから
  逆引きは導出データとして各 DBノードが手元で再構成する(I4)。
- 帰結 3: 保持は言明の外、レコード層(ref・pin)から宣言される。言明は自分自身の保持を
  主張できない。保持させたいのに、どの保持宣言からも前方に辿れないものは、束ねの言明
  (索引)を作ってレコード層から指す(検証記録がこの例になる)。

## 原理 4(真理の層の分離): 一次言明・検証・訂正・追随は別の種類の言明である

この四つを混ぜないことが、この設計の中心である。

- 一次言明は世界について述べる(blob B のページ p に節 T がある)。原理 1 の列挙では
  チャンク・doc_rev・注釈がこれにあたる。
- 検証記録は照合の実施について述べる(方法 M と根拠 E でこの照合を行った)。真理を作らず、
  信頼の根拠を足すだけである。照合が通っても真とは限らず(十分条件ではない)、真でも
  照合に落ちうる(個人ラベルの注釈がその実例。手動確認の経路が要る理由)。
- 訂正(corrects 型)は言明の真偽について述べる(X は誤りで、Y が代わる)。訂正それ自体も
  言明なので誤りうるし、相反する訂正が共存できる。どれを信じるかは見えと読み手の側の
  判断であり、データ層は裁定しない(開世界)。
- 追随(supersedes 型)は対象の変化について述べる(Y は X の新版対応物)。X の真偽には
  触れない。旧言明は旧 blob についての真のままである。
- 帰結: 照合を通った言明への訂正は、異常系ではなく正常系である。検証は訂正を不要に
  しない。

## 原理 5(見えと歴史の分離): 見えは張り替え、歴史は消えない

- ref は単一書き手の署名付きポインタであり、いまの見えを表す。既定の読み手(検索・RAG)は
  見えだけを読む。
- 旧版・旧言明・訂正は、版の連なり(doc_rev の previous)と訂正・追随の辺から辿れる形で
  残る。監査する読み手は歴史を辿れる。
- 帰結: 「取り消し」は見えからの除去(tombstone)であって、言明の消滅ではない。言明を
  世界から消す操作はこの層に存在しない(物理的な回収は保持と容量の問題であり、真理の
  問題ではない)。

## 原理 6(内容への繋留): 名前は可変、内容は不変 — 主張は内容に張る

- 名前(ref のパス、仕様書の識別子)は可変な指示子であり、同じ名前が時刻によって別の
  内容を指す。
- 世界について述べる言明は、名前ではなく内容(blob のハッシュ)に張る。注釈のページずれ
  (実装計画の前提節にある、os_dev_specs の data.md で実際に起きた事故)は、可変な名前に
  主張を張ったことの帰結だった。内容に張れば、版の更新は「同じ文書の変化」ではなく
  「新しい内容の出現」になり、旧い主張は偽にならない。
- 名前の役割は一つだけになる: いまこの名前はこの内容を指す、という見えの入口(原理 5)。

## 原理のあいだの緊張

- 「歴史は消えない」(原理 5)は論理の側の主張であり、物理の保存を約束しない。SPEC は
  古いレコードの忘却と、複製要求のない言明を世界が忘れることを設計として許している。
  正確に言えば: 消えていない限り、歴史は常に辿れて意味が定まる。保存そのものは保持宣言
  (pin)と健全性の領分である(原理 3 帰結 3)。
- 「いっしょに運ぶ」(原理 3)の代価は重さである。訂正を受け取る者は旧言明と根拠も
  受け取り続ける。監査可能性のためにこの重さを受け入れる、というのがこの設計の選択で
  ある。

## 捨てた代替(論理レベル)

- 言明の上書き(可変な注釈): 帰属と歴史が消え、署名の対象が動く。原理 1 と両立しない。
- 検証を言明の内容に埋める: 検証のやり直しが言明の同一性を変える。原理 2 と原理 4 の
  混同。
- 訂正を削除で表す(旧言明の tombstone だけで済ます): 除去の事実は署名付きレコードとして
  伝播するが、なぜ消えたか・何が代わりかは言明として残らない。tombstone は見えの操作で
  あって主張ではないからである。原理 4 と原理 5 に反する。
- 双方向参照: content-addressing では作れず(原理 3 の位相順序)、必要でもない(逆向きは
  導出データ。原理 3 帰結 2)。

## 実装計画との対応(この文書の検収の仕方)

この文書の完了条件は、実装計画([docs/plan/INGEST.md](#11ff6fec-cf85-4ae9-a24c-6098964f6cce))の
すべての設計判断が上の原理から導出できることである。導出できない判断が見つかったら、
原理か判断のどちらかが間違っているので、どちらかを直す。主要な対応:

- doc_rev に時刻を入れない・再取り込みの同一性判定 ← 原理 2(帰結 1)
- 検証記録の自己完結 ← 原理 2(帰結 2)と原理 3(帰結 1)
- 注釈索引の ref ← 原理 3(帰結 3)
- corrects と supersedes の型の分離・訂正対象の出どころ ← 原理 4
- 注釈を文書名ではなく blob ハッシュに張る ← 原理 6
- 逆引き索引を導出データとして持つ ← 原理 3(帰結 2)。なお「遅延構築にする」という
  時期の選択は原理からは出ない実装判断(起動経路の堅牢性)であり、導出の検収対象では
  ない。

実装の着地時には、冒頭の位置づけのとおり本文書を docs/design/ へ移す。移動の作業項目は
実装計画の後始末の一覧に載っている。
