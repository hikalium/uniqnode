## 直近のマイルストーン: 取り込み

いまの uniqnode は器としては完成しているが中身が空で、「文書」を知らない。この
マイルストーンが終わると、次のことができるようになる。

- 手元の Markdown のノート一式と、仕様書 PDF 25 本を、コマンド一発で投入できる。
- 入れた資料のどの断片についても「どの文書の、何番目の、どの見出しの下、PDF なら
  何ページ」という引用元が引ける。
- 「ACPI 6.4 の 162 ページは Generic Address Structure の節」のような注釈 100 件が、
  機械検証つきで載る。
- 注釈に誤りが見つかったら、削除ではなく「これは誤りで、こちらが正しい。理由と根拠は
  これ」という訂正をグラフに発行できる。

つまり「知識の器」から「引用できる知識庫」への一歩である。検索は次のマイルストーンだが、
検索が返すべき「出典付きの断片」がこの段階で全部そろう。

工程は六つの段で、前の段が次の段の土台になる。

1. 切る(チャンカー)。文書を、検索と引用の単位になる断片に切る純粋な関数。長すぎると
   引用として読めず、短すぎると文脈が消えるので、上限はおよそ 480 トークン相当。
   Markdown は見出しの区切りを優先し、各断片に「どの見出しの下にいたか」のパンくずを
   持たせる。
2. 書き込む。原文(blob)・断片(chunk)・断片を順序付きで束ねた版(doc_rev)・現行版を
   指す名札(ref)をこの順でストアに書く経路。合格条件は「同じものをもう一度入れたら、
   何も起きないこと」。内容が住所になる仕組みが正しく効いていれば再投入は完全な
   空振りになるはずで、それ自体が設計の検証になる。
3. 入口を付ける。コマンドと HTTP API。対象外のファイルは黙って捨てずに一覧で報告する。
4. PDF 対応。テキスト抽出は pdftotext という既存ツールへの外注(ライブラリ依存ゼロの
   方針のまま)。ページをまたぐ断片は作らず、各断片が自分のページ番号を持つ。引用に
   「何ページ」と出せるのはこのため。
5. 注釈を入れる。「このページはこの節」という注釈 100 件を読み込む。ここに検証の門が
   ある: 注釈のタイトルと実際にそのページにある本文とを照合し、合わないものは入れずに
   報告する。先日ページずれを 33 件見つけた手作業の検証を、仕組みに昇格させる。機械
   照合に落ちるが人間が確認済みのものは、「人手で確認した」という記録を付けた上で
   だけ入れられる。黙った例外は作らない。
6. 訂正を発行する。誤った注釈を見つけたら「新しい言明・誤った言明・理由・検証記録」を
   結んだ訂正の辺を発行し、古い注釈側から訂正を発見できる逆引きも作る。

完了条件の正典は [docs/plan/INGEST.md](#11ff6fec-cf85-4ae9-a24c-6098964f6cce) の
完了条件の節にある。

## なぜこの形か(一段だけ深く)

この層の設計には出発点になった実話がある。手元の Intel マニュアル等への注釈 100 件を
検証したら 33 件がページずれしていた。原因は、PDF が改版されたのに注釈が「sdm_vol3
という名前」を指していたこと。教訓は一つ: 主張は可変な名前ではなく、不変な内容
(ハッシュ)に張る。そうすると改版は「同じ文書が変わった」ではなく「新しい内容が
現れた」になり、古い注釈は間違いに転落せず「旧版についての真」のまま残る。

それでも本物の誤りはあり、オブジェクトは不変なので直せない。だから訂正も言明として
足す。すべて署名付きなので、誰がいつなぜ直したかが残り、相反する訂正が共存でき、
どれを信じるかは読み手の側に残る。LLM が古い引用で答えてしまっても、「この言明への
訂正はあるか」を後から辿って検証し直せる、というのが RAG としての効き目である。
原理の全体は [docs/plan/ASSERTIONS.md](#c05379e2-2d30-41bc-8342-62103d94bb21) にある。
