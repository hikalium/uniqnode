# LOGGING — 運用ログ(既定でファイルに残す・UTC の時刻・大きさによる回転)

<a id="14a4e260-70af-4c52-9f19-1c116bddd004"></a>

読み手は、serve・mcp・viewer を常駐させて使う者と、node/src/log.rs を読む者。この文書は運用ログの
現在の実装を記述する。検索の劣化や取り込みの拒否といった個々の診断が何を言うかは
[docs/design/SEARCH.md](#19574e78-9bf5-4f87-a4c2-c4a10222c580) と
[docs/design/MCP.md](#dacd474d-424a-45d5-a278-766fc2465dd9) にあり、ここが決めるのは
その行がどこへ、どんな形で残るかだけである。

## 既定で残す

ログは後から読むためのデバッグ資料であり、失うほうが問題である。だから常駐する 3 つ、
serve・mcp・viewer は、何も指定しなくてもログをファイルに残す。シェルのリダイレクトを
書き忘れたら失われる、という置き方をしない。

- serve: 前景で走らせているあいだは端末に見えているが、常駐させれば端末は消える。
- mcp: 標準エラーは登録した LLM クライアント(Claude Code など)が吸うので、そもそも利用者の
  目に触れない。失われやすさは serve より大きい。
- viewer: serve と同じ。serve の隣で常駐し、転送先に届かなかったことなどを残す。

標準エラーへの出力はやめない。ファイルと標準エラーの両方に、同じ 1 行が出る。前景で見た行が
そのままファイルに残っていなければ、後から読む者は 2 つの記録を突き合わせられない。

## 置き場と名前

| 命令 | 既定の道 |
|---|---|
| serve | `<data_dir>/logs/serve.log` |
| mcp | `<data_dir>/logs/mcp.log` |
| viewer | `<data_dir>/logs/viewer.log` |

データディレクトリの下に置くのは、ログがそのストアについての記録だからである。ストアを複製・
移動すれば、その走行の記録も一緒に動く。そこに書けないとき(他人の所有する 0750 のストア)
だけ、利用者の書ける場所へ倒す(下の「開けなかったとき」)。役割ごとに別のファイルなのは、
同じデータディレクトリに対して serve と viewer が 1 本ずつと mcp が何本も同時に走るためで
ある(mcp は会話ごとに 1 本立つ)。

ログはストアの容量計算に入らない。`node.json` の `capacity_bytes` と `GET /v1/status` の
`used_bytes` が数えるのはオブジェクトのバイト数だけで、ログの 40 MiB はそれとは別に載る。

SPEC §5.1 との関係。§5.1 の「ディスク上のファイルは 2 種類だけ」は、ストアのデータ、すなわち
オブジェクトと reflog の置き方を縛る規定である(クラッシュ整合性・無停止バックアップ・世代
管理がその規律に還元される、という節そのものの理由づけによる)。ログはストアのデータではない。
中身は運用の記録で、内容アドレスも seq も持たず、失っても回復に要らず、fsck の対象でもない。
同じ意味でデータディレクトリの下に住む運用ファイルは既に `node_key`・`node.json`・`peers.json`・
`groups.json`・`derived/` がある。SPEC 側にはこの区別を明示する一文を足してある。

## 行の形

```
2026-08-17T03:22:08Z [pid 1536836] uniqnode: search: 低情報チャンク 1 件を応答から落とした(…)
```

- 先頭は UTC の時刻(`2026-08-17T03:22:08Z`)。機械や時間帯をまたいでも突き合わせられる。
  描画は [docs/design/MCP.md](#dacd474d-424a-45d5-a278-766fc2465dd9) の出典の取得日時と同じ
  node/src/clock.rs の 1 箇所から出る(should/0135)。
- 次が `[pid <番号>]`。同じ `mcp.log` に複数の会話が同時に追記するので、どの会話の行かを
  後から分けられるようにする。
- 残りが元の診断そのものである。

## 出口は 1 箇所

出す側は `log_line!` だけを使い、node/src/log.rs の `write_line` が行の形も出力先も決める
(should/0135)。時刻の付け方を変えるにも、保存先を増やすにも、直すのはこの 1 箇所である。

使い分けは次のとおり。常駐する serve・mcp・viewer の診断は `log_line!` を通す。usage の説明文と、
一回きりの命令が返す結果の行(fsck の異常一覧、sync の集計、cert-verify の判定、ingest の
取り込み報告)はその命令の出力であってログではないので、これまで通り println!/eprintln! で出す。

## どれくらいの速さで太るか(実測 2026-08-17)

実コーパス(25443 オブジェクト、ACPI 仕様の PDF)を開いた serve に対し、本番の呼び手である
MCP アダプタ経由で要求を投げて測った(should/0138)。

| 状態 | 出る量 |
|---|---|
| 要求が来ない(健全性エンジンが 5 秒周期で回るだけ) | 60 秒で 0 バイト |
| 要求が来ない(届かないピア 1 つ + 満たせない pin 1 つ) | 60 秒で 0 バイト |
| 検索 1 件(埋め込みサーバが健全) | 224 バイト |
| 検索 1 件(埋め込みサーバに届かない。最悪) | 425 バイト |

読み取れることは 2 つある。第一に、常駐しているだけでは太らない。健全性エンジンの周期実行は、
接触の失敗を沈黙として扱うので 1 行も出さない。第二に、太る速さは検索の回数にだけ比例し、
最悪でも 1 件 425 バイトである。回転の設計はこの数字から決めてある。

## 回転

- 1 世代の上限は 8 MiB。越えたら `serve.log` を `serve.log.1` へ送り、`serve.log.1` は
  `serve.log.2` へ、という具合に押し出して、新しい `serve.log` を開く。
- 保持する古い世代は 4 つ。溢れた `serve.log.5` にあたるものは消える。
- したがってディスクの上限は 8 MiB × (1 + 4) = 40 MiB で頭打ちになる。上の実測では、最悪の
  検索 425 バイトで数えて 1 世代あたりおよそ 2 万件、全体でおよそ 10 万件ぶんの履歴にあたる。
- 1 行が上限より大きくても、その行は必ず書く。空の世代を作りながら回り続けない。
- 追記で開くので、再起動しても前回の走行の記録は消えない。消えるのは回転で溢れた世代だけである。
- fsync はしない。std::fs::File は buffer を持たないので 1 行ごとに OS へ渡り、プロセスを
  kill -9 で裂かれても直前の行までは残る。機械ごと落ちたときの末尾は保証しない。

## 上書きの手立て

serve・mcp・viewer が持つ(常駐する命令だけがログをファイルに残すため。fsck や backup のような
一回きりの命令の出力は結果であってログではない)。

| 指定 | 効き |
|---|---|
| `--log <path>` | 保存先を変える。親ディレクトリは作らない(在ることを求める)。開けなければ倒さない(下) |
| `--no-log` | ファイルへ残さず標準エラーだけに出す |
| `--log-max-bytes <n>` | 1 世代の上限を変える(既定 8388608) |

`--no-log` を与えたときは、残さないことを起動時に標準エラーで言う。黙って記録を止めない。

## 開けなかったとき・書けなくなったとき

ログを書けないことは、答えられる要求を断る理由にはならない。提供できる仕事があるのに記録の
都合で起動を止めるほうが損である(should/0114)。ただし黙って落とさず、どこへ残したか、
あるいはなぜ残せなかったかを必ず言う(must/0022)。倒すか否かと倒す先の判断は node/src/log.rs
の `open_default` と `fallback_path` にあり、serve・mcp・viewer は main.rs の `start_logging`
1 つを通してそれを呼ぶ(should/0135)。

- ログはデータのディレクトリもその祖先も作らない(docs/plan/APPEND_FAILURE.md の方針 1a。
  ログが先にデータのディレクトリを作ると、ストアの「親が無ければ断る」が効かなくなる)。
  既定の道では `logs/` の 1 段だけを `mkdir` する。ストアを開く serve と mcp(ストアを直接
  開く形)は、既定の道を使うとき、ログを開く前にデータのディレクトリを検めて `mkdir` し、
  親が無ければ標準エラーにだけ理由を言って 1 で終わる。倒す先(下)だけは祖先ごと作る。
- 既定の道(`<data_dir>/logs/<役割>.log`)が開けない(ディレクトリを作れない・書けない)
  ときは、利用者の書ける場所へ倒す。倒す先は `$XDG_STATE_HOME/uniqnode/logs/<役割>.log`、
  XDG_STATE_HOME が無い(空も無いとみなす)なら `~/.local/state/uniqnode/logs/<役割>.log`。
  systemd の user 単位の %S と同じ決め方で、利用者が状態の置き場として既に持っている場所を
  使い、新しい規約を増やさない。倒したときはその事実と両方の道を、この走行の最初の 1 行
  として標準エラーとファイルの双方に出す(どちらの記録からも、どこに残したかが読める):

  ```
  2026-09-05T08:55:52Z [pid 856878] uniqnode: mcp: 既定のログ先 /var/lib/uniqnode/logs/mcp.log に書けない(Permission denied (os error 13))ので /home/op/.local/state/uniqnode/logs/mcp.log に残す
  ```

  続く起動の記録「ログを … に残す」も倒れ先を言う。動機は system 単位のストア(0750、所有者
  uniqnode)に人間の権限で mcp を起こす形([docs/mop/SYSTEMD.md](#7de68e4a-e6a6-4930-8cc7-a56f90f522e2))
  で、既定の道には書けず、標準エラーは LLM クライアントが吸うので、倒さなければ誰も読めない
  記録になる。
- 倒す先が無い(XDG_STATE_HOME も HOME も取れない)か、倒す先も開けないときは、両方の道と
  それぞれの理由を標準エラーに言い、標準エラーだけに出して走り続ける。
- `--log <path>` で明示された道が開けないときは倒さない。どの道でなぜ失敗したかを標準エラー
  に言い、標準エラーだけに出して走り続ける。利用者が指した道を黙って別の場所に変えると、
  指した所を読みに行った者が何も見つけられない。倒すのは既定の道のときだけである。
- 走行中に書けなくなったとき(ディスクが埋まったなど)は、その事実を 1 度だけ言ってファイルを
  閉じ、以後は標準エラーだけに出す。毎行同じ苦情を繰り返さない。

## 意図的に持たないもの

- 段階(debug/info/warn の区別)。今あるのは「運用者が読むべき事実」だけで、量も上の実測の
  とおり少ない。段階を付けるのは、絞り込みが要るほど出るようになってからでよい。
- 時刻による回転(日次のファイル分け)。大きさで頭打ちにすれば足りる。
- 複数プロセスで書くときの排他。同じ `mcp.log` へ追記する会話は pid で見分ける。追記は O_APPEND
  なので行が混ざることはなく、回転が同時に起きても失うのは古い世代だけである。
- MCP の `logging` capability。あれはサーバがクライアントへログを送るプロトコル機能で、
  実装していないものを capabilities に載せない([docs/design/MCP.md](#dacd474d-424a-45d5-a278-766fc2465dd9))。
