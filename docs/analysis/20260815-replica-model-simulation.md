# レプリカ・健全性モデル(SPEC §8)のシミュレーション検証

<a id="31e38823-b783-4dfe-bc7c-3cd268f5e7b4"></a>

日付: 2026-08-15。対象: SPEC.md §8(版0.1)。手段: sim/ クレートの決定論的シミュレータ
(1 tick = 1 単位時間、依存なし、種を与えた自前乱数のみ)。

## 方法

- 各 tick で「レコード交換の配送 → 各DBノードが tick 開始時点の状態だけを見て判断 → 適用 → evict →
  レコード交換の送信 → 神視点の計測」を行う。判断と適用を分けているため、複数DBノードの同時判断に
  よる競合(同時修復・同時降格)が現実と同じ形で起こる。
- 既定パラメータ: 交換周期 5、配送遅延 1〜3、生存信号タイムアウト 15、T_prop 20、
  T_heal 100、転送時間 3、降格猶予 20。
- シナリオテスト 8 本(sim/tests/scenarios.rs、`cargo test` で決定論的に再現)と、
  種 200 個 × 2 シナリオの掃引(`cargo run --release`)。掃引では配送遅延の上限と降格猶予を
  種ごとに振り、観測ゆらぎの幅を広げた。

## 結果

シナリオテスト(すべて成功):

| シナリオ | 検証内容 |
|---|---|
| 保持者1台の脱落 | DEGRADED 遷移 → rendezvous 修復 → SATISFIED。取得者は不足数ちょうど(1台)。ALERT なし |
| 容量の構造的不足 | T_heal を待たず ALERT(capacity)。観測者ごとに1回だけ(遷移でのみ)発火 |
| 取得元の全喪失 | 修復不能のまま T_heal 経過で ALERT(unknown)。保持者の復帰で SATISFIED に回復 |
| 分断と合流 | 両側が独立修復して4複製 → 合流後、降格2回で2複製に収束。複製数が min を割った tick は 0 |
| min_replicas=0 | 作成者の複製を含め全所から evict され消滅。警報なし(仕様どおりの意味論) |
| evict の保護 | 確約層は evict されない。ローカル確約層から参照される機会層オブジェクトは温存 |
| 雪崩の不在 | 不足2に対し取得者は最大2台 |
| 反復故障 | 保持者を8回落として復帰させても収束し、自傷 breach は 0 |

掃引(200 種 × 2 シナリオ、計 400 実行):

| 指標 | 分断合流(min=2, 6台) | 反復故障(min=3, 8台) |
|---|---|---|
| 収束(期待複製数への到達) | 200/200 | 200/200 |
| min 割れが起きた種 | 0 | 200(故障直後の実不足。下記) |
| 自傷 breach(全台生存中の min 割れ) | 0 | 0 |
| breach 区間の長さ 平均/最大 | - | 36 / 38 tick |
| 同時取得の最大 | 2(片側1台ずつ) | 1 |
| 1実行の降格回数の最大 | 2 | 4 |
| 誤警報(ALERT 遷移) | 0 | 0 |

## 発見事項(仕様へ反映)

1. 保持表明には生存の割引が必須(仕様の欠落 → SPEC §8.2 に追記)。
   保持表明は撤回されない限り view に残るため、脱落したDBノードの表明をそのまま数えると
   不足が永遠に検知されない。「直近の生存信号(レコード交換の受信)が T_hb 以内の保持者の表明だけを
   数える」という規則が必要で、T_hb はプロトコルの必須設定値である(T_hb < T_prop)。
2. 修復遅延の下限は T_hb + T_prop + 転送時間(SPEC §8.2 に注記)。
   反復故障掃引の breach 区間長(平均 36、最大 38 tick)は理論値 15 + 20 + 3 = 38 と一致する。
   故障からこの時間は実複製数が min を下回る。この窓の間の追加故障に耐えたい データは、
   その分 min_replicas を上げる必要がある(min=2 は「1故障に耐えるが、修復窓の間は無防備」)。
3. 降格規則(SPEC §8.3 の4条件)は観測ゆらぎの下で安全(確認)。
   400 実行で自傷 breach は 0。同時降格が起きても「自分を除いた観測数 ≥ min」の条件が
   下限を守る。合流後の過剰解消も降格回数ちょうど(余分な昇降の振動なし)。
4. 状態機械の遷移について(SPEC §8.4 の表現を調整)。
   不足検知(T_prop 経過)と容量の回復不能判定が同時に成立する場合、実装は SATISFIED から
   ALERT(capacity) へ1遷移で報告する。DEGRADED を経由した2遷移を要求しない。

## 限界(今後の検証課題)

- レコード交換は全対全の直接送信で、中継・メッセージ損失(分断以外)を扱っていない。
- 取得は開始時に取得元が存在すれば必ず成功する(途中喪失・帯域の奪い合いは未モデル)。
- pin とオブジェクト仕様は全DBノードに既知(pin 自体の伝播遅延は未モデル)。
- T_prop / T_heal / T_hb の設定値がDBノード間で食い違う場合の挙動は未検証。
- should/0137(欠陥復元によるテストの証明)は初回スイートのため未実施。仕様変更でテストを
  改訂する際に順守する。
