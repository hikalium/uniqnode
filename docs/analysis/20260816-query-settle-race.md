# 分散クエリ試験の単発失敗の根本原因: 即時決着とピア応答の競走

<a id="30f14fdd-778d-4906-88bb-8cc70c05c8b2"></a>

日付: 2026-08-16。対象: L2 分散クエリの統合試験
`knowledge_held_by_one_peer_is_found_within_budget`。
発端: ワークスペース全体の実行で2度、テスト名を控えないまま1本が落ちた。

## 特定の手順(名前を失った失敗の追い方)

集計だけを見て名前を控えなかったため、最初は再現も特定もできなかった。特定できたのは、
失敗時の集計値「108 passed / 1 failed」とスイート別本数の累計を突き合わせたからである。
lib 76 + api 5 + crash 1 + eval 4 + groups 3 + health 2 + ingest 12 = 103 で、次の
query.rs は 6 本。つまり 103 + 5 = 108 が通り 1 本が落ちた地点は query.rs の中しかない。
cargo test は失敗したスイートで停止するので、以降のスイートが走っていないことも
この読み方を裏づける。

対象を query.rs に絞り、プロセス生成負荷(48 並列で短命プロセスを回す)をかけて
12 回実行したところ 2 回再現した。負荷なしの通常実行では 13 回連続で緑だった。

## 機構

クエリの決着規則は「object の回答が得られたら即 found」である(node/src/query.rs の
finalizer)。スコープに 2 台(持たない B、持つ C)を置いた場合、C の回答が着いた瞬間に
決着するので、B がまだ答えていなければ B の状態は pending のまま報告される。

試験は B の状態を empty と決め打ちしていた。empty は「自分は持たない」という肯定的
言明であり、pending は「まだ何も言っていない」である。開世界の意味論ではこの二つは
別物で、決着が速ければ pending が正しい報告になる。負荷がかかると C の応答が B の応答に
先着する確率が上がり、露見した。

実装は仕様どおりであり、欠陥は試験の側にあった。

## 対処

B の状態への表明を集合(empty または pending)に緩め、なぜ両方が正しいのかを
失敗時のメッセージと注釈に書いた。空応答と沈黙の区別そのものは、決着を待ってから読む
`silence_of_the_only_holder_times_out_without_nonexistence_claims` が担っており、
受け入れ基準の被覆は落ちていない。

## 教訓

- 早期決着する仕組みの試験で、決着に関与しない側の状態を決め打ちしてはならない。
  観測できるのは「決着時点のスナップショット」であって、全員の最終状態ではない。
- 集計だけを見て走らせると、失敗したテストの名前が失われる。名前を失っても、
  スイート別本数の累計から落ちた場所は絞り込める。以後はテスト出力をファイルに残す。
