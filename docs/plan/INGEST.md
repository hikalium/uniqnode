# INGEST — 取り込み(チャンキング・文書モデル・PDF・注釈)と訂正表現の実装計画

<a id="11ff6fec-cf85-4ae9-a24c-6098964f6cce"></a>

読み手はこの作業単位を実装する者。[docs/plan/RAG.md](#2e00cbd1-45df-4b4f-8b47-c0b57c298f9e) の
取り込みの項と [docs/plan/RAG.md](#bf3ef713-3971-403a-88e7-93bc647db29c) の訂正のグラフ表現の
項を、着手できる具体度まで確定するのがこの文書の仕事である。目的は一つ: 手元の文書群
(Markdown・プレーンテキスト・PDF)を uniqnode に取り込み、各チャンクの引用元(文書名・
文書内位置・見出し・PDF はページ番号)を引ける状態にする。BM25 検索
([docs/plan/RAG.md](#35a888f7-5ac6-4333-831c-dd7753b82315) の項)はこの計画に含めない。

## 前提と依存

- SPEC の適合レベル L0〜L4 は実装済み。本計画はコアの kind(node/edge/blob)と
  到達閉包の規約(c1 値中の s256: 文字列を参照と見なす。SPEC §4.3)だけに依存し、
  コア・プロトコル・ストレージ形式には変更を加えない。上位層 kind の追加は SPEC §4.3 が
  許している(MAY)。
- PDF のテキスト抽出は pdftotext(poppler)への外部プロセス委譲。llama-server(埋め込み)・
  curl(HTTPS)と同じ「ライブラリ依存はゼロ、外部プロセスは可」の枠。sudo なしで
  apt-get download と dpkg -x により ~/opt/poppler/ へ導入できることは確認済み
  (検証済みの版: poppler-utils 22.02)。
- 注釈索引の実データは os_dev_specs の data.md(spec_id ごとの見出し + 表題・形式・URL の
  コードブロック + 「p.N: 節タイトル」の箇条書き。注釈 100 件)と、os_dev_specs_private の
  PDF 25 本(ファイル名は <spec_id>.pdf。PDF の SHA-1 台帳は data.md ではなく同リポジトリの
  index.txt にある)。注釈は 2026-08-16 に全件を PDF の現行版と照合済みで、内訳は機械照合
  99 件 + 手動確認 1 件(「CPUID list」。個人ラベルのため紙面見出しと機械的には一致しない)。

## この計画で確定する判断

### 文書モデル(上位層 kind)

blob(原文そのもの)・chunk(検索と引用の単位)・doc_rev(版)・ref(現在の見え)の4層。

```jsonc
// chunk: 引用に必要な文脈を自身で持つ
{ "v": 1, "kind": "chunk", "text": "…",
  "meta": { "breadcrumbs": ["5 …", "5.2.3.2 …"], "page": 162 } }

// doc_rev: 原文 blob と順序付きチャンク列を束ねる版
{ "v": 1, "kind": "doc_rev", "source": "s256:<blob>",
  "chunks": ["s256:…", "s256:…"],
  "meta": { "name": "acpi_6_4", "media": "pdf", "extractor": "pdftotext 22.02" },
  "prev": "s256:<前版の doc_rev>" }   // 初版は prev キーなし
```

- ref `collections/<コレクション名>/<文書名>` が現行の doc_rev を指す。文書一覧は
  既存の refs 一覧(GET /v1/refs)で足りるので、新しい一覧 API は作らない。
- 引用は doc_rev 側から組み立てる: 文書名は ref 名、文書内位置は chunks 列の添字、
  見出しは meta.breadcrumbs、PDF はさらに meta.page。チャンク単体から出発する逆方向
  (このチャンクはどの文書のものか)は、作業手順の段 6 の逆引き索引が与える。
- チャンクの順序は doc_rev の chunks 列だけが持つ(順序は辺が持つ、という I7 と同じ形)。
  chunk 自身に番号を持たせず、同じ判断を二箇所に置かない(should/0135 の同型)。
- doc_rev に時刻を入れない。入れると同一内容の再取り込みが別 ID になり、べき等(I1)が
  壊れる。取り込み時刻は ref レコードの at(可変層・署名付き)が既に持っている。
  不変データと可変メタデータの分離(I4)の帰結。
- 捨てた代替案: chunk が本文を持たず blob へのオフセット参照だけを持つ形。保存の重複は
  減るが、引用とスニペット返却のたびに blob の取得と切り出しが要る。同一本文のチャンクは
  content-addressing が自動で重複排除する(効くのは再取り込みと文書内の繰り返し。
  改版をまたいで page や breadcrumbs が変われば別の言明になり、排除しないのが意図)ので、
  重複の実コストは小さい。

### チャンキング規則

- 大きさはトークン近似で上限 480。検索スニペットとして読める長さと、埋め込み入力
  (bge-m3 系)に収まる長さの兼ね合いで、400〜512 トークン相当の幅から選んだ値。
- 近似は「ASCII 文字は 1/4 トークン、非 ASCII 文字は 1 トークン」の重み付き文字数と
  する。この近似は純関数 token_estimate として一箇所に置き、チャンカーとテストが
  共用する(should/0135)。
- Markdown: 見出し境界を優先し、段落単位で上限まで詰める。見出しの入れ子パスを
  各チャンクの meta.breadcrumbs に写す。
- PDF: pdftotext の form feed をページ境界として保存し、ページをまたぐチャンクを
  作らない(引用のページ番号を一意にするため)。ページ内は段落単位で詰める。
- プレーンテキスト: 空行区切りの段落単位で詰める。
- 捨てた代替案: 正確なトークナイザの導入。依存ゼロ方針と衝突するうえ、チャンク境界の
  質は評価ハーネス([docs/plan/RAG.md](#8912f7c0-05fd-464d-9cba-4db8a5d30527) の項)で
  測って調整するほうが確実。

### PDF 抽出

- pdftotext は Command で直接起動する(シェルを経由しない。must/0009 と同じ理由)。
  実行ファイルは引数 --pdftotext <path> の明示指定を優先し、無指定なら PATH を引く。
  見つからないときは、必要なバイナリ名と sudo なしの導入手順(前提節)を示して明示的に
  失敗する。黙って PDF を飛ばさない(must/0022 の同型)。
- doc_rev.meta.extractor に抽出器の名前と版を記録する。poppler の版が変わると抽出
  テキストが揺れうるが、blob は PDF そのものなので、再抽出の差は新しい doc_rev に
  なるだけで、旧 doc_rev は旧抽出についての真のまま残る(I1)。

### 注釈索引の取り込みと検証

- data.md を読み(spec_id 見出し + コードブロック + 「p.N: 節タイトル」行)、注釈 1 件を
  annotates 型の辺として取り込む:

```jsonc
{ "v": 1, "kind": "edge", "type": "s256:<annotates 型ノード>",
  "members": ["s256:<節タイトルのノード>", "s256:<PDF blob>"],
  "meta": { "page": 162 } }
```

- 参照先は文書名ではなく PDF blob のハッシュ(I1)。spec_id から blob への解決は、
  先に取り込み済みの PDF の ref(collections/<コレクション名>/<spec_id>)を引いて
  doc_rev.source を使う(したがって注釈の取り込みは PDF の取り込みの後)。PDF の版が
  変われば新しい blob になり、旧注釈は旧版についての真のまま残る。data.md のページずれは
  可変な名前(sdm_vol3)に注釈を張ったことの帰結であり、この規律が事故クラスそのものを
  消す。
- 取り込み時に注釈タイトルと当該ページ本文を照合し、不一致は取り込まずに報告する。
  照合規則(2026-08-16 の data.md 検証で用いた方法の規則化): 小文字化して英数字以外で
  分割し、数字だけのトークンを除いたうえで、タイトル側トークンの 6 割以上が当該ページ
  本文のトークン集合に含まれれば一致。一致に使った本文行を根拠として検証記録(訂正の
  表現の節)に残す。照合は一つの関数に置き、取り込み時検証と再検証(訂正の根拠づくり)が
  共用する(should/0135)。
- 機械照合で一致しないが人が正しいと確認した注釈(現在 1 件: CPUID list)は、method を
  manual とした検証記録を付けて取り込める。黙った例外は作らず、記録が残る形だけを許す。
- 型ノード(annotates / corrects / supersedes)の c1 本文は定数として一箇所に定義し、
  生成側と判定側が同じ定数を使う(must/0023)。

### 訂正の表現

この計画で「言明」と呼ぶのは、グラフに置かれた個々の不変オブジェクトのことである
(ここでは主に annotates 型の辺。corrects の members には任意のオブジェクト ID を置ける)。

```jsonc
// 検証記録: 照合の方法と根拠を残すノード
{ "v": 1, "kind": "node", "contents": { "verifies": "s256:<対象の言明>",
  "method": "token-match", "evidence": ["CPUID—CPU Identification"] } }
// method は token-match(機械照合)または manual(人手確認)

// corrects 辺: 誤りの訂正
{ "v": 1, "kind": "edge", "type": "s256:<corrects 型ノード>",
  "members": ["s256:<新しい言明>", "s256:<誤った言明>"],
  "meta": { "reason": "…", "verification": "s256:<検証記録>" } }
```

- corrects 型の辺: members は [新しい言明, 誤った言明] の順。meta.reason に理由、
  meta.verification に検証記録の ID を置く。meta 内の s256: 文字列も参照なので
  (SPEC §4.3)、到達閉包が根拠ごと運ばれる。
- supersedes 型の辺: 文書の新版に伴う張り替え。members の順序は corrects と同じく
  [新しい言明, 旧い言明]。誤りの訂正とは別の型として区別する(旧言明は旧 blob について
  真のままであり、誤りだったわけではない)。doc_rev.prev が同名文書の版の連なりを
  自動で持つのに対し、supersedes は注釈のような個別の言明の追随を明示に張る。
  本計画で実装するのは型定数と辺の形の確定までで、発行経路は改版追随が実際に必要に
  なったときに足す。
- 現在の見えは ref が決める。検索と RAG が既定で使うのは ref の指す doc_rev に載った
  現行言明だけで、旧言明と訂正辺は履歴として辿れる。
- 逆引き(あるオブジェクトを参照する既知オブジェクトの一覧)を導出データ(I4)として
  起動時走査で構築する。参照抽出は既存の collect_references を使う(should/0135)。
  これにより「この言明への訂正はあるか」が、旧言明しか持たない DBノードでも問える。

## 作業手順(各段に確認方法を付す)

1. ingest モジュール(node/src/ingest.rs)に token_estimate とチャンカー(Markdown・
   プレーンテキスト・ページ分割)を純関数で実装する。
   確認: ユニットテスト(境界・meta.breadcrumbs・ページ保存・同一入力から同一チャンク列)。
   token_estimate 自体のテストは期待値をリテラルで書く(検査対象から期待値を導出しない)。
2. ストアへの書き込み経路: blob + chunk 群 + doc_rev + ref を一括で書く。再取り込みの
   no-op 判定は取り込み経路が現行 ref を読んで行い、target が一致すれば set_ref を
   呼ばない(set_ref 自体は変更しない。既存の set_ref は同一 target でも新レコードを
   追記する)。
   確認: 再取り込みで ID 集合と ref の seq が変わらないこと(べき等 = I1 の検証)。
3. CLI `uniqnode ingest <data_dir> <コレクション名> <パス>`(ディレクトリは再帰、拡張子で
   種別判定)と API `PUT /v1/collections/{c}/documents/{name}`(本文 = 生バイト列、種別は
   {name} の拡張子で判定)。CLI は排他ロックのため serve 停止中のストア用であり、usage に
   その旨を明記する(serve 中は PUT API を使う。既存 sync サブコマンドと同じ扱い)。
   確認: 統合テスト。実プロセスに生 HTTP/1.1 で当てる(should/0138)。CLI は実プロセスで
   起動する。
4. PDF 抽出(pdftotext 委譲)とページ対応チャンキング。
   確認: 手書きの最小 PDF をテスト資材(ソースとは別ファイル。should/0112)に置き、
   ページ番号付きチャンクが出ること。pdftotext 不在の環境ではテストを黙って飛ばさず、
   導入手順を示して失敗する(openssl 相互検証テストと同じ扱い。2026-08-16 の操作者
   裁定で、外部コマンド前提のテストは不在時に失敗へ統一した)。
5. 注釈索引の取り込み(data.md パーサ + トークン照合検証 + annotates 辺の発行)。
   確認: cargo test には data.md の抜粋と不一致を人工的に作った資材を置き、「一致は入り、
   不一致は取り込まず報告」を両向きに確認する(発火を一度も見ていない検証器は未検証の
   ため、負例を必ず含める)。実データ 100 件(機械照合 99 + manual 1)の投入は private な
   資材に依存するため、自動テストではなく完了条件の手動受け入れとして行う。
6. 訂正の発行経路: `uniqnode correct <data_dir> <誤った言明ID> <新しい言明ID> <理由>` が
   新しい言明を再照合して検証記録を作り、corrects 辺を発行する。逆引き索引と
   GET /v1/objects/{id}/referrers を実装する。
   確認: 段 5 の不一致資材から訂正済み注釈を入れて corrects 辺を発行し、referrers で
   旧言明側から訂正が見つかること。

順序の理由: 段 1〜3 は Markdown だけで完了条件の前半を満たす最短列。PDF(段 4)と
注釈(段 5)はその上に載り、訂正(段 6)は段 5 の検証機構を前提にする。

## リスクと戻し方

- すべて追加であり、既存のコア(kind の解釈・プロトコル・ストレージ形式)に変更はない。
  途中で失敗しても既存機能は壊れない。
- 取り込みの取り消しは ref の tombstone(既存機能)で現在の見えから外せる。参照されない
  オブジェクトは無害に残り、物理回収は pack GC
  ([docs/plan/RAG.md](#4ed764d8-a570-4809-bd0c-80de0d4b5545) の項)の領分。
- pdftotext の版差で抽出が揺れる危険は、doc_rev.meta.extractor の記録と
  content-addressing(PDF 抽出の節)で吸収する。

## 完了条件

- Markdown ディレクトリを一括で取り込め、同一内容の再取り込みが no-op で、各チャンクの
  引用元(文書名 = ref 名、文書内位置 = chunks 列の添字、見出し = meta.breadcrumbs)が
  doc_rev 経由で引ける。
- os_dev_specs_private の PDF 25 本と注釈 100 件(機械照合 99 件 + manual の検証記録付き
  1 件)が投入でき、チャンクと注釈の引用に PDF ページ番号が出る。
- 注釈の検証不一致から corrects 辺を発行でき、referrers で旧言明側から訂正が見つかる。
- 着地後の後始末: 確定した文書モデルと訂正モデルを SPEC §9 の正典化として写し、
  本文書は削除する(must/0013)。
