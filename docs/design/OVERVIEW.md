# OVERVIEW — uniqnode とは何か(やさしい解説・現在の姿)

<a id="cfa85cc2-0d72-49f2-b628-b9622589851b"></a>

自分の資料(ノート・仕様書 PDF・ウェブの保存)を全部入れておき、LLM が出典付きで引ける
記憶装置を目指すシステム。ノートと PDF とウェブの頁を入れて LLM から出典付きで引くところ
までは 1 台で動いており、将来は自宅と実家のように複数台で知識を持ち合う。この文書は、
実装済みの土台をやさしい日本語で説明する。規範は SPEC.md、未実装の層の解説は
[docs/plan/OVERVIEW.md](#4e00f8f7-7cb7-4aff-8ed8-17d94ff56071) にある。

## 土台: 内容がそのまま住所になる

すべてのデータは「中身のハッシュ値 = 名前」で保存する。中身が 1 文字でも違えば別の
名前になる。この方式の帰結として、同じものを二度入れても増えず(自動の重複排除)、
名前さえ知っていれば中身の改竄を必ず検出でき、一度生まれたオブジェクトは二度と
変わらない。「上書きで直す」「消す」という操作は、この世界にはそもそも存在しない。

では世界はどう変わるのか。変化は二種類だけである。新しいオブジェクトを足すことと、
「いまどれが現行か」を指す名札(ref)を張り替えること。名札は各ノードが自分の署名付きで
書く可変なレコードで、時刻や「どれが現行か」のような運用情報はすべてこちら側に置く。
不変な「主張」と可変な「運用」を混ぜない、というのが設計全体を貫く分離である。

## 中身はグラフ

オブジェクトは 3 種類だけ: 生のバイト列(blob)、頂点(node)、辺(edge)。辺は「どういう
関係か」を表す型も頂点で持ち、2 個以上のメンバーを順序付きで束ねられる。オブジェクトの
中に現れるハッシュ参照は「これを運ぶときはあれも一緒に運ぶ」という宣言で、参照を辿った
一式(到達閉包)が複製や保存の単位になる。

## 分散と「開世界」

ノード同士は手動で登録した相手とだけつながり、署名付きレコードを定期的に交換する
(伝播交換)。ここに大事な約束がある: 「見つからない」は「存在しない」を意味しない。
沈黙は情報ゼロである。だから問い合わせの答えは「見つかった」「自分の知る範囲には無い」
「時間切れ」の三通りで、データ層は決して「この世に無い」とは言わない。

## 覚えておく責任

保存の約束は pin で表す: 「この根から辿れる一式を最低 N 台で持て」。各ノードは
「私は持っている」という保持表明を交換し合い、台数が足りなくなったら自分で取り寄せて
修復する。逆に複製要求ゼロのものは「世界が忘れてもよい」データである。

## 信頼は鍵で表す

ノードは鍵ペアで識別する。グループの公開鍵と k-of-n の証明書(たとえば家族の管理者
2 人が署名したノードは仲間、のような規則)で参加を管理し、鍵を 1 本外せば、その鍵が
関与した発行物はまとめて自動失効する。

## いまどこまで動くか

上記の土台(単一ノードの保存・複製・分散問い合わせ・レプリカ健全性・グループ鍵)は
すべて実装済みで、SPEC の適合レベル L0〜L4 に対応する。その上の取り込み層も実装済みで、
Markdown・プレーンテキスト・PDF・HTML の文書を引用元(文書名・位置・見出し・ページ番号)
付きで入れられ、機械検証つきの注釈の取り込みと、誤りへの訂正の発行・逆引きが使える
([docs/design/INGEST.md](#47d69a3e-c39a-4e76-9814-e9c24240293b))。入れた原本はバイト列の
まま返せるので、PDF は PDF として、保存した頁は頁として読み直せる
([docs/design/RENDITION.md](#6046eeca-1d95-4d47-87da-13f86c7710dc))。その上の検索層も実装
済みで、語がそのまま一致する問いにはキーワード検索(BM25)、言い換えや別の言語のように語が
一致しない問いには意味検索(文をベクトルに直して近さで測る。ベクトルの計算は外部の埋め込み
サーバに任せる)、両者の順位を融合したハイブリッドが使える。方式を指定しなければ、埋め込み
サーバを備えているかと、何件返すかで自動的に選ばれる。どの方式でも出典(引用の各フィールド)
付きの断片が返る([docs/design/SEARCH.md](#19574e78-9bf5-4f87-a4c2-c4a10222c580))。検索の
当たり具合を数値で測る仕組みもあり、決まった小さな資料と「この問いにはこの断片が正解」の対を
用意して、検索のやり方を差し替えながら数値を比べられる
([docs/design/EVAL.md](#1109a04b-923e-4493-8f00-d704047d6a2a))。

いちばん上には LLM エージェント向けの窓口が載る。標準入出力で MCP(Model Context Protocol)を
話すアダプタがあり、Claude Code のようなエージェントに登録すると、検索の search と全文取得の
fetch の 2 つの道具として見える。返る答えには出典(文書名・ページ・見出し・チャンクの ID・
その版を取り込んだ日時)が並ぶので、エージェントはどこから引いたかを示して答えられる
([docs/design/MCP.md](#dacd474d-424a-45d5-a278-766fc2465dd9))。常駐する 2 つ(serve と MCP
アダプタ)は、何が起きたかの記録を既定で `<データディレクトリ>/logs/` に残す。端末を離れても
失われず、大きさで回転するので際限なく太りもしない
([docs/design/LOGGING.md](#14a4e260-70af-4c52-9f19-1c116bddd004))。ここまでで「自分の資料を
LLM から出典付きで引ける記憶装置」は 1 台のノードとして成立している。

同じ知識は人の目からも引ける。serve の隣で 1 枚の HTML のビューワを起こすと、ブラウザから
検索し、出典をたどり、PDF の紙面や保存した頁を原本のまま開ける
([docs/design/VIEWER.md](#4cd4c71a-ecf3-44a8-a97b-bb2c8d8fe847))。

知識は 1 台に閉じない。検索の問いは登録したピアへ配ることもでき、各ノードが自分の索引で
検索して自分の上位だけを順位として返し、返ってきた順位をまとめて 1 本の答えにする。順位
だけを使うので、ノードごとに検索のやり方や埋め込みの模型が違っていてもよい。問いには
送り主の署名が付き、受け取った側は「知っているノードか」「そのノードへ見せてよいコレク
ションはどれか」を自分の設定で決めてから答える
([docs/design/DISTRIBUTED_SEARCH.md](#e577f6db-659e-4eb8-a152-3b7780e4a9d1))。この先に載る層
(運用の仕上げ)は [docs/plan/OVERVIEW.md](#4e00f8f7-7cb7-4aff-8ed8-17d94ff56071) を参照。
