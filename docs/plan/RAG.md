# RAG: LLM から使える検索ストレージへ

<a id="86363f4a-3df6-4aa2-9c64-b99aa5cb4e7b"></a>

現在の状態: SPEC の適合レベル L0〜L4(単一ノードストア・レプリケーション・分散クエリ・
レプリカ健全性・グループ鍵)に加えて、取り込み層
([docs/design/INGEST.md](#47d69a3e-c39a-4e76-9814-e9c24240293b))、BM25 検索
([docs/design/SEARCH.md](#19574e78-9bf5-4f87-a4c2-c4a10222c580))、検索方式を差し替えて
数値で比べる評価ハーネス([docs/design/EVAL.md](#1109a04b-923e-4493-8f00-d704047d6a2a))
まで実装済み。テスト134本、CLI + HTTP API。
ゴールは、このシステムを RAG ストレージとして LLM エージェントから常用できる状態に
すること。以下は実行順に並べた作業項目(先頭は 4 の埋め込みとハイブリッド検索。4〜5 が
ゴール達成の最短経路で、済んで削除された項目の番号は再利用しない)。

## 4. 埋め込みとハイブリッド検索

llama-server(`/v1/embeddings`、bge-m3 想定)への HTTP クライアント。ベクトルは
(chunk, embedder_id) キーの導出層(全走査コサイン。RAM に載る規模では ANN 不要)。
BM25 と RRF で融合。llama-server に届かないときは BM25 のみに劣化して動き続ける。
先に、評価ハーネスの固定コーパスへ今の BM25 が取りこぼす対(言い換え・同義語のように
クエリと正解が語をほとんど共有しないもの)を足す。現在は 13 対すべてが 1 位で指標が
上限に達しており、このままでは改良を数値で見られない
([docs/design/EVAL.md](#1109a04b-923e-4493-8f00-d704047d6a2a))。
完了条件: 言い換えクエリで意味検索が効き、評価ハーネスで BM25 単独より Recall@k が
上がることを数値で確認。

## 5. MCP アダプタ

search / fetch の2ツールを公開する stdio モード(`--mcp`)。コアはあくまで REST で、
MCP は薄い被せ物(rag_plan の設計判断)。
完了条件: Claude Code に登録し、エージェントが出典(引用元+取得日時)付きで回答できる。
ここで「LLM から使える RAG ストレージ」が成立する。

## 6. 分散検索(kind: search)

QUERY メッセージ署名(要求者の認証)と応答側の trust_level フィルタを入れた上で、
検索クエリを登録ピアへ散布し、各ノードのローカル top-k を RRF で統合する
(順位ベースなのでノード間のスコア較正が不要)。
完了条件: SPEC §7.1 の kind:search が動き、2ノードに分かれた知識が1クエリで返る。

## 7. 運用の仕上げ

systemd unit の例、バックアップ手順(封印セグメントの rsync + 復元検証)、README の運用節。
完了条件: 常用ノードが systemd で動き、バックアップからの復元手順が一度実証されている。

## 8. pack GC(機会層 evict の物理回収)

<a id="4ed764d8-a570-4809-bd0c-80de0d4b5545"></a>

pack の書き直しで evict 済みオブジェクトのディスクを回収し、その上で min_replicas=0 の
LRU+参照カウント evict(SPEC §5.4)を有効化する。容量の小さいノードを本格運用する前提。

## 9. 失効文とグループ設定の伝播交換への載せ替え

現状は groups.json への手動配置。署名済み文書なので伝播交換に載せる素地はある。

## 10. その先

Web スナップショット(rag_plan の W トラック)、mgcanvas 形式エクスポートによる可視化、
Contextual Retrieval・リランカーなどの検索品質向上(評価ハーネスで測りながら)。
